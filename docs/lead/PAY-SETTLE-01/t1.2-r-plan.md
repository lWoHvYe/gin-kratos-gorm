## 2. 修复设计

### B1 真实生命周期

1. `TccCancelMarkPaid` 入口 gate 允许：`PENDING_PAYMENT`、`PAID`、`ALLOCATED`、`SHIPPED`、`COMPLETED`；`refund_state=REFUNDING` 走 Tx1 resume（注意 `REFUNDING` 是 refund_state，不是订单 status）；`CANCELLED + paid<=0` 幂等；`CANCELLED + paid>0` **不得静默成功**，返回 `FAILED_PRECONDITION`（T1.6 支付级取消退款未完成）或交给 T1.6；`MANUAL_HOLD/FAILED_PERMANENT` 不得 resumable，返回冲突/人工。
2. `tccCancelDecision`：
   - `PENDING_PAYMENT`：`paid<=0` 本地取消；`paid>0` → R-3 guard（T1.6）。
   - `PAID/ALLOCATED/SHIPPED/COMPLETED`：`paid<=0` keep-paid（无资金可退）；`paid>0` → `tccCancelRefund`。
3. 退款分支按现有 Tx1 建 batch/application/permit；已离仓组按 R-2 的 shipment facts 返回 POST；不得回滚订单生命周期，不写 `CANCELLED`。
4. `MANUAL_HOLD/FAILED_PERMANENT` 必须从 resumable 集合移除；否则 T1.2-R 会绕过人工挂起。
4. 测试必须使用真实投影状态：
   - `ALLOCATED + G1 SHIPPED`；
   - `SHIPPED` / `COMPLETED`；
   - 多组：一组 SHIPPED、一组未离仓；
   - `PAID + group SHIPPED` 仅作兼容，不替代真实状态。
5. 不再用“未知状态静默成功”；未知/无法判定 fail-closed。

### M1 历史 composition

1. `composition_known=0` 的组：允许**整组退款**，组上限 MUST 用 `CapCent = groupPaid + freight_share - RESERVED/SETTLED`，**不得**用旧 commitment 的 amount（那是已占用额度，不是本次可退上限）；不要求 `order_refund_commitment_lines`；不得按行部分退款。
2. `writeTccBatchGroupsTx` 在循环前只加载**需要行组成**的组；`composition_known=1` 才校验行合计；新 TCC commitment 使用 `composition_known=0`/无行（系统责任整组）。
3. 测试使用迁移后形状（`goods=amount/freight=0/known=0`，无行），断言整组 TCC 不被阻断；`known=1` 行合计错误仍 fail-closed。
4. 不自动归因历史行；需要部分退款时转人工。

### M2 无活动组

- **Σ 校验必须先于 no-active 判断**：`active=0 && remaining>0` 必须写 `PRECHECK_FAILED` 审计（不得提前成功）；`Σ=0` 且 `remaining=0` 才不写 `REFUNDING`、不建 batch/application，返回幂等成功；不得产生空 FROZEN batch。
- 若订单已是 `REFUNDING` 且有 batch，resume 只补缺，不创建空 batch。
- 测试：全部已退/零活动组、`refund_state=FULL`、投影滞后。
