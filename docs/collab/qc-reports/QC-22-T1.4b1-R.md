## 1. B1 外部退款部分打款与 RefundBatch 原子性

| 点 | Plan 落点 | 判定 |
|---|---|---|
| 问题 | §1：Payment per-call cap 下 G1 6000 成功、G2 4000 被拒 → 部分打款；preflight/重读无法消除窗口 | **成立** |
| 原子批退款 | §2：新增 `RefundBatch(payment_no, batch_id, items[{refund_id,amount}], reason)`；intent 行锁内校验 `Σ items == B` 且 `Σ items <= captured - refunded`；不满足 `INSUFFICIENT_REMAINING/BATCH_SUM_MISMATCH` 且**零写入**；全部 item 同一事务写 refunds/outbox；全成功或全失败；`batch_id` 幂等 | **满足 AC-65“不得部分打款”**：Payment 原子批是决定性机制，Order 预检只缩小窗口、不承担原子性 |
| 事件 | 每 item 发 `refund_id`；Order 收敛 commitment/app/batch | **可接受**；与 `GetRefundByKey`/`payment.refunded` 一致 |
| 回退 | §3.6：不逐组退化为 `Refund` | **正确**；否则重新引入部分打款 |

## 2. Order 预检 B/done/inFlight/outstanding/R

- §3 的 `B = batch.sum_group_cap_cent`（冻结）、`R = captured - refunded`、逐 application `GetRefundByKey` 分类（done/inFlight/outstanding/unknown）、`B == done+inFlight+outstanding`、`R == B - done`、`unknown==0`，否则 `MANUAL_HOLD`、零 Payment。**逻辑自洽**：只有 `inFlight==0` 才调用 `RefundBatch`；`inFlight>0` 只收敛同 `refund_id`；不开始新组。
- 外部退款 1000/6000/4000：`R` 变化 → `R == B - done` 不成立 → `MANUAL_HOLD`、零 `RefundBatch`；若外部退款发生在预检后、`RefundBatch` 前，Payment 的 `Σ <= captured-refunded` 行锁校验会整体失败/零写入，不会部分打款。**覆盖 AC-65**。
- 事件丢失：`GetRefundByKey` 成功 → done，不重付；batch 不提前 DONE；in-flight 不开始新组。**符合**。

## 3. C-04 契约是否足够

- `RefundBatchRequest` 的 `payment_no/batch_id/items/reason` 足以让 Payment 做“按 intent 原子批”；`RefundBatchReply` 的 `batch_id/status/refunded_cent` 足以让 Order 收敛；`batch_id` 作为幂等键、`refund_id` 作为 item 幂等键，与现有 `refunds` 的 `idempotency_key` 兼容。
- **结论：C-04 足以实现 AC-65 的“不得部分打款”**，无需新增 Payment 表或 Order 迁移。

## 5. 非阻断提示（实现前建议补进 C-04/RΣ2/RΣ3）

1. **`batch_id` 幂等的内容校验**：同一 `batch_id` 重复请求若 items 不同（金额/组集合），仅返回“同结果”会掩盖调用方错误。建议 `RefundBatch` 持久化该 batch 的 item 集合（或 Σ 的 hash），重复请求时校验一致，不一致返回 `BATCH_ID_CONFLICT` 且零写入。
2. **`B` 与外部退款的竞态**：Order 预检的 `B` 是 T1.2 冻结的 `sum_group_cap_cent`；若外部退款发生在 T1.2 之后、T1.4b1 之前，`R < B - done` 会 `MANUAL_HOLD`，这是正确 fail-closed；建议测试矩阵明确“外部退款 1000 后不自动重算 B、转人工”，避免实现偷偷下调 B。
3. **`RefundBatch` 的失败分类**：瞬时（DB/网络）保持 `PAYING` 重试；`INSUFFICIENT_REMAINING/BATCH_SUM_MISMATCH/BATCH_ID_CONFLICT` 判 `MANUAL_HOLD`；不得把判定性失败重试成部分成功。建议在 RΣ2 的验收里列出三类的精确映射。
4. **测试矩阵**：已含外部 1000/6000/4000、in-flight、事件丢失、幂等、并发；建议补“同一 `batch_id` 不同 items”“预检后外部退款”“`RefundBatch` 成功但事件丢失后重放”三条，绑定真实 MySQL + `-race`。
