# T-002 三条协作闸门可执行化

## 提问（PO）

**背景**：`docs/collab/CONVENTIONS.md` §4 已定义三条闸门，但目前只是文字约定，没有任何机器拦截。已经发生过一次真实漂移：PO 在 20:57 裁决完 P-01…P-18，ADR §19.2 仍写着"待 PO 裁决"。

**诉求**：把三条闸门做成**可本地执行、可接进 `make verify` / CI** 的检查，失败必须指名道姓（哪个文件、哪个 AC、哪个版本）。

| 闸门 | 必须检查 | 失败条件 |
|---|---|---|
| G-1 所有权 | 依据 commit 的 `Role:` trailer 与变更路径比对：`docs/specs/**` 仅 PO、`docs/adr/**` 仅 Architect、`docs/implementation/**` 仅 Developer、`docs/po/**` 仅 PO | 角色与路径不匹配；允许 `Role:` 多值或 `Exception: T-NNN` 显式豁免，但豁免必须出现在输出里，不得静默 |
| G-2 版本 | Spec 正文变更时 YAML `version` 必须升；`docs/specs/README.md` 索引版本必须与 YAML 一致；变更记录必须出现新版本号 | 版本未升 / 索引不同步 / 变更记录缺失；纯链接与错别字修正可用 commit `Non-normative: true` 豁免 |
| G-3 AC↔测试 | 从 Spec 抽取 `AC-NN`，在 `*_test.go` 中查引用（`TestAC<NN>` 或注释 `AC-<NN>`） | strict 模式下存在未覆盖且无 `owner`+`expiry` 的 AC |

## PO 对实现方式的约束（不指定技术方案）

1. **两档模式**：日常 `make verify` 用 warn（打印覆盖率与违规提示，不阻断）；发布/合并前用 strict（阻断）。理由是开发早期 AC 必然未全绿，天天红会让闸门失去威信。
2. **覆盖台账**：strict 模式需要的 AC 覆盖清单由 **Reviewer** 维护（PO 不写测试台账，Reviewer 才对测试负责）；未覆盖项必须带 `owner` + `expiry`，与 CONVENTIONS §6 的偏差规则一致，到期未清即失败。
3. **不得依赖网络、Docker 或外部服务**；本地单机 5 秒内跑完。
4. **只读历史提交，不修改 git 历史**；检查结果必须可复制进交付说明。
5. **不得为了过闸门而放宽规则**：例如把 AC 从 Spec 删掉、把路径挪到豁免名单。这类"绕过"要在 ADR 里明令禁止。

## 验收（PO 视角，Reviewer 执行）

- **A1**：用 `Role: Developer` 改一个 `docs/specs/*.md` → 检查失败，输出指出该文件。
- **A2**：改 Spec 正文但不升 `version` → 失败；升了但索引没同步 → 失败。
- **A3**：删掉某条 AC 的唯一测试 → strict 失败并列出该 AC 编号。
- **A4**：正常提交 → 三项通过，`make verify` 绿。
- **A5**：本地执行耗时 < 5 秒。
- **A6**：故意在提交里加 `Non-normative: true` 但实际改了业务规则 → 由 Reviewer 人工打回（机器无法判断语义，接受这条人工兜底）。

## 回写（Architect）

- 在 ADR 或 CONVENTIONS 附录写明检查项、豁免键（`Role:` / `Exception:` / `Non-normative:`）与两档模式的调用方式；
- 指定 Developer 实现，实现后由 Reviewer 跑 A1…A5；
- 完成三者后把本线程改为 `CLOSED` 并填 `closed_by`。

## 关闭条件

方案已回写 + 实现已合并 + A1…A5 有可复现的终端证据（贴进本线程"验证"段）。
