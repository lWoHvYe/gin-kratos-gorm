## 0. 一页决策摘要

1. **v1 的「整行选单仓」被废止。** 现有 ADR 0002 与基线 INV-10 规定「单行数量不跨仓」，导致单仓不足即整单拒绝。本 Spec 改为：**同一 SKU 的数量可以按仓拆成多条订单行**，拆量发生在支付之前，支付之后仓/组快照冻结。
2. **三条不可谈判底线**：
   - 用户**不得因为商家分仓而多付运费**（现行"每组各收一笔运费"必须改）。
   - 用户**必须在付款前**知道这单会分几个包裹、来自几个仓，不允许付款后才告知。
   - 退款金额**由规则计算**，不再由申请方填写金额（现行缺口）。
3. **承运商从"自由文本"升级为受控业务对象**，签收事实只能来自物流签收事件或用户主动确认，客服不得直接改签收。
4. 本 Spec **废止**基线 INV-10，其余 INV-01…INV-16 全部继续有效；新增 INV-17…INV-29。
5. 下列三项**不在本期**，Architect 不得擅自纳入：多仓秒杀、支付后重新分配、已支付未发货的"按组取消"。

## 1. 业务目标与成功指标

### 1.1 目标

| 目标 | 说明 |
|---|---|
| G1 提高可成交率 | 单仓不足而总量充足的订单不再被拒单，改为拆量成交 |
| G2 不因拆单损害用户体验 | 运费不重复收取、包裹数可控、付款前知情 |
| G3 售后按数量可算清 | 部分数量退货的金额、回库仓、额度三者唯一且可追溯 |
| G4 签收事实可信 | 签收只来自物流或用户，杜绝"客服手工改已收货" |

### 1.2 业务指标（上线后按月看）

- 拆单率 = 拆量订单 / 全部订单；目标区间 5%–20%，超过 20% 说明库存布局有问题，需业务侧处理，不是放宽规则。
- 因拆单向用户多收运费金额：**恒为 0**。
- 拆单订单售后率相对非拆单订单的差异：不得高于 1.5 倍。
- 缺货拒单率（下单时总量不足）：环比下降。
- 签收后争议率（用户申诉"未收到但显示签收"）：≤ 0.5%。

## 2. 范围与非目标

### 2.1 本期范围

1. 按数量拆行：同一 SKU 在多个仓之间按数量拆分订单行。
2. 选仓优先级的**业务序列**（不定义算法，只定义业务偏好顺序）。
3. 拆量下的运费、优惠分摊、退款基准与部分数量售后。
4. 承运商与运单号受控、物流轨迹状态、签收驱动收货、拒收/丢件/破损的判责入口。
5. 用户可见性：付款前的拆单告知、付款后的组级物流展示。

| 非目标 | 理由 |

| 支付后重新分配仓库或重新拆量 | 快照冻结是退款可算清的前提 |

## 3. 术语

| 术语 | 定义 |
|---|---|
| 行（line） | 订单中"一个 SKU + 一个仓库 + 一个数量"的原子销售单元 |
| 履约组（group） | 一个仓库对一个订单的履约单元，一个组对应一个包裹；组号如 `G1` |
| 拆量（quantity split） | 用户下单数量被拆到多个仓，形成多条同 SKU 的行 |
| 行实付额 | 该行应付给商家的商品金额 = 行单价 × 行数量 − 该行优惠分摊额 |
| 行剩余可退额 | 行实付额 − 该行已退（含在途占用）金额 |
| 单次退款额 | 本次退货数量对应的可退金额，受行剩余可退额封顶 |
| 签收 | 承运商确认包裹已交付，或用户在订单详情主动确认收货 |
| 异常轨迹 | 拒收、退回、丢失、破损四类承运商异常 |

## 4. State Ownership（状态所有权）

### 4.1 所有权矩阵

| # | 业务事实 | 唯一所有者 | 允许的取值 | 谁可以改变 | 严禁 |
|---|---|---|---|---|---|
| S1 | 订单生命周期 | Order | `PENDING_PAYMENT / PAID / ALLOCATED / SHIPPED / COMPLETED / CANCELLED` | 支付确认、首组运单创建（发货授权）/发货/收货投影、取消 | 写入退款态；用"部分完成"等组合值 |
| S2 | 订单履约投影 `shipment_status` | Order | `UNSHIPPED / PARTIALLY_SHIPPED / SHIPPED / PARTIALLY_RECEIVED / RECEIVED` | 由组状态聚合 | 前端/客服自行推导 |
| S3 | 履约组履约状态 | Order（组的唯一所有者） | `PENDING / ALLOCATED / SHIPPED / RECEIVED / CANCELLED` | 收款、运单创建/发货、收货、整单取消（持久化 `CANCELLED` 仅由整单取消写入）；退款撤许可只改 S5，不写 S3 | 由运单状态反推订单生命周期；退款写组 `CANCELLED` |
| S4 | 履约组退款态 | Order | `NONE / REFUNDING / REFUNDED` | 收款/售后事件投影 | 与 S1 合并；一个字段同时表达"已收货/已回库/可退款" |
| S5 | 发货许可 | Order | `NONE / CONSUMED / REVOKED` | 发货授权、退款拦截 | 由 Fulfillment 自行判断可发 |
| S6 | 运单状态 | Fulfillment | `CREATED / SHIPPED / RECEIVED / CANCELLED` | 发货、签收、组退款作废 | 改写订单生命周期 |
| S7 | **签收事实** | **承运商轨迹事件或用户确认**（Order 只消费） | `已签收 / 未签收 / 争议中` | 物流签收事件、用户主动确认、仲裁结论（留痕）；已确认后的争议**不回滚**收货事实 | 客服直接置为已签收；由发货时间推算；已确认后回滚 receipt |
| S8 | 物流轨迹 | Fulfillment | 见 6.8 | 承运商回传 | 客服手改轨迹 |
| S9 | 售后流程状态 | AfterSales | `REQUESTED / APPROVED / REJECTED / RETURNING / RETURN_RECEIVED / REFUNDING / REFUNDED` | 审核、寄回、回库、退款 | 写入金额或回库结论 |
| S10 | 售后申请额度 | AfterSales | `ACTIVE / CONSUMED / RELEASED` | 申请、审批、完成 | 释放已消耗额度 |
| S11 | 回库状态 | AfterSales | `NONE / PENDING / PROCESSING / DONE / FAILED_PERMANENT`；`NONE` 仅表示"不适用"（如 `REFUND_ONLY`），**禁止 NULL 或空串** | 回库任务 | 回库未完成即退款 |
| S12 | 实际打款事实 | Payment | captured / refunded | 支付回调、退款执行 | 未校验上限即打款 |
| S13 | 真实库存 | Inventory | 可售 / 预留 / 已出库 | 预留、确认、释放、回库 | 由展示库存反推 |
| S14 | **行已退数量 / 行已退金额** | **AfterSales（唯一）** | 非负整数 | 售后审核与退款完成 | Order 自建"已退数量"第二事实源 |

### 4.2 所有权铁律

1. **S1 与 S4 永不合并**：订单生命周期不得写入 `REFUNDING / PARTIALLY_REFUNDED / REFUNDED / CLOSED`；"全部退款"只能作为**展示结论**由 S1+S4 推导，不得落成生命周期值。
2. **S3 与 S6 永不互相反推**：运单 `RECEIVED` 只驱动组进入 `RECEIVED`；组 `SHIPPED` 不得由客服手工置位。
3. **S7 不接受"估算"**：任何"已签收"的展示必须有签收事件或用户确认作为证据；无证据时只能展示"运输中/待确认"。
4. **S14 只有一份**：售后退了多少件、退了多少钱，只能有售后侧的台账；订单侧任何展示值都是只读投影。
5. **拆量不引入第五套状态**：行只有 `(SKU, 仓库, 数量, 组)` 四个属性，**行不设独立状态机**；行的取消/退款由组与售后表达。
6. **“组关闭”不是新状态字段**：它是由 S3 组状态、S5 许可与 Order 的组退款准入结果（RefundAdmission，owner=Order）派生的只读结论（AC-27A）；不得为它新增持久化字段，也不得用它替代 S5/S4（组退款态 `refund_state`；SPEC-0002 编号为 S9）或反推运单事实。

## 5. 业务不变量（Invariants）

> 基线 INV-01…INV-16 继续有效。**INV-10（"单行数量不跨仓"）自本 Spec 生效起废止**，由 INV-17、INV-19 替代。

| ID | 不变量 | 反面即违规 |
|---|---|---|
| INV-17 | **数量守恒**：订单所有行数量之和 = 用户下单数量；任意时刻该 SKU 已退数量 + 剩余数量 = 下单数量 | 拆量后多出或少掉 1 件 |
| INV-18 | **单行单仓**：一条行只属于一个仓库、一个履约组；跨仓只能体现为多条行 | 一条行横跨两个仓 |
| INV-19 | **拆量上限**：同一 SKU 最多拆 2 条行；整单最多 3 个履约组；超限必须拒绝并提示 | 为凑库存拆成 4 个包裹 |
| INV-20 | **运费只收一次**：用户支付的运费 = 订单级一次计算结果；各组运费之和在内部口径必须等于它 | 两仓收两次运费 |
| INV-21 | **金额守恒**：Σ 行实付额 + 运费 = 订单实付；Σ 行退款额 ≤ 订单实付 | 退款后金额对不上 |
| INV-22 | **支付后冻结**：支付成功后，行、组、仓的分配快照不可变更、不可重算 | 支付后换仓、加组 |
| INV-23 | **退款基准唯一**：单次退款额只由行实付额与退货数量决定，不接受调用方填写金额 | 用户自填退款金额 |
| INV-24 | **退款额度双层校验**：售后额度 ≤ 行剩余可退额，同时 ≤ 订单 captured 剩余；两层都通过才可打款 | 只查一层导致超退 |
| INV-25 | **签收单调**：已签收不可被运输中轨迹拉回；争议中可覆盖为"争议"并冻结自动确认 | 轨迹乱序把已签收改回运输中 |
| INV-26 | **缺货不静默**：支付后缺货不得换仓、不得降级拆量、不得静默退款，必须显式通知并二选一 | 用户收不到货也没人告知 |
| INV-27 | **售后单属于单一组**：一张售后单只能覆盖一个履约组的行 | 一张售后单跨两组退款 |
| INV-28 | **可追溯**：每一次拆量决策、签收判定、退款计算，必须能回答"为什么是这个结果" | 客服无法解释为何分两个包裹 |
| INV-29 | **责任判定结构化**：判责只接受枚举与证据引用，自由文本不得作为判责依据；运费判定不得阻塞商品退款 | 看到 reason 里写"破损"就判承运商；拖判责导致商品也退不了 |

## 6. 业务规则

### 6.1 拆量判定（付款前）

对每个 SKU 的请求数量 Q：

| 情形 | 规则 |
|---|---|
| 存在单仓可售 ≥ Q | **不拆量**，该行整行落一个仓 |
| 无单仓满足，但多个仓合计 ≥ Q | **拆量**：按 6.2 的优先级选出最少的仓数，把 Q 分成 2 条行（默认上限 2） |
| 合计可售 < Q | **拒绝该次下单**，并明确返回"本仓可售最大数量"与"减少数量后可单包裹发货"的提示；不得先收款后告知 |
| 拆量所需仓数 > 2 | **拒绝**，提示最大可下单量或建议分单购买 |
| 整单组数将超过 3 | **拒绝**整单成交，提示"库存分散，请拆分为多笔订单" |

补充规则：

- 拆量只拆**数量**，不拆"单件"以外的东西：数量必须是整数件，不得出现半件、不得拆套装内单品。
- 拆量后每条行保留原 SKU 的**同一单价**；拆量本身不得改变价格、不得改变优惠。
- 拆量必须在**付款前**完成并展示；付款后不接受任何形式的重新分配（INV-22）。
- 秒杀订单**不参与**拆量：秒杀活动绑定单仓，库存不足即失败（本期非目标）。

### 6.2 选仓优先级（业务顺序，硬约束）

同等可行性的方案之间，严格按下列顺序取舍：

1. **可行性**：所有被选仓的可用量之和 ≥ 请求量；任一仓不可用即淘汰。
2. **包裹数最少**：能用 1 个仓就不用 2 个；能用 2 个不用 3 个。
3. **集中度最高（数量口径）**：同等仓数下，优先让"数量最多/可用量最大"的仓吃满，减少后续再拆。**不引入商品金额或价格参与选仓**——价格是 Pricing 的事实，分配只认库存事实；且拆量不改单价，同一 SKU 各行单价相同，"数量集中"与"金额集中"结论一致。
4. **仓库业务优先级**：按甲方配置的主仓/区域仓优先级（当前只有单仓，配置为默认值）。
5. **可用量降序**：可用库存更多的仓优先，降低并发下的失败概率。
6. **稳定确定性**：以上全部相同，按仓库固定顺序决定，保证同一请求多次预览结果一致。

禁止：按"运费最低"选仓（运费由 6.4 统一定价，不参与选仓）；按"客服手工指定"选仓；跨仓调拨补货。

### 6.3 拆量后的订单结构

- 一个订单包含 1…3 个履约组；每个组恰好对应一个仓库、一个包裹。
- 同一 SKU 可出现 2 条行，分别属于不同组；行数量之和 = 用户下单数量（INV-17）。
- 组号 `G1…Gn` 按 **warehouse_id 升序** 编号，与仓库业务优先级无关（优先级只决定"选哪个仓"，不决定编号）；编号一旦生成在订单生命周期内不可变，重复预览必须得到同一编号。
- 一个组只能整体发货：不允许"组内再拆包"；一个包裹只属于一个组。

### 6.4 运费与优惠（红线）

1. **运费只向用户收一次**：以订单商品实付总额判定包邮门槛（现行 99 元/10 元参数沿用，业务可调），**不按组判定、不按组累加**。
2. 组级运费只作为**内部成本分摊**（按组商品金额比例），不得出现在用户应付金额里重复计算；各组内部分摊之和必须等于用户支付的运费（INV-20）。
3. 运费优惠（免邮券/包邮活动）**只作用于订单级运费**一次，减免到 0 为止；不做"按 G1…Gn 逐组抵扣"，也不改变各组内部分摊口径。减免后如需内部展示组份额，按组商品金额比例分摊**剩余运费**（末组吸收差额）。
4. **商品类优惠**（满减/商品券/活动）按行商品金额比例分摊到行，采用**最大余数法**：每行先取整数分，剩余的分按"小数部分从大到小、并列按行号升序"逐分分配，保证 Σ 行优惠 = 订单商品优惠，且每行与理论值偏差 ≤ 1 分。**运费券/免邮不属于商品优惠**：只减运费、不摊入行优惠、不改变行实付额与退款商品金额。
5. 用户在任何页面看到的应付金额 = Σ 行实付额 + 运费，且与支付金额一致；拆单前后同一购物车的商品金额与优惠不得变化。

### 6.5 退款基准与部分数量售后

| 规则 | 内容 |
|---|---|
| R1 行实付额 | 行单价 × 行数量 − 该行优惠分摊额（6.4.4） |
| R2 行实付单价 | 行实付额 ÷ 行数量，向下取整；行最后一次退款时补足差额 |
| R3 单次退款额 | 行实付单价 × 本次退货数量；行剩余可退额不足时按剩余额封顶 |
| R4 上限 | 本次退款 ≤ 行剩余可退额，且 ≤ 订单 captured 剩余（双层校验，INV-24） |
| R5 退货数量上限 | 行数量 − 该行已退数量；超退必须拒绝，不得"按金额折算" |
| R6 售后归属 | 一张售后单只属于一个组；同 SKU 跨仓的两条行必须分别申请，不得合并（INV-27） |
| R7 回库仓 | 退回商品回**原发货仓**；跨仓回库为显式例外流程，需客服授权并留痕，本期不做自动流转 |
| R8 金额来源 | 退款金额由系统按 R1–R4 计算并展示，**任何角色（含申请方、客服、管理员）都不得直接改金额**；审批只能通过调整**退货数量**来表达，金额随数量重算（P-06）。填写金额只作为"用户期望"记录，不参与计算。历史单（无行快照）的兼容改额路径仅限该历史单，必须记录判定人、依据与授权，**不得对新单开放**，且必须有移除期限（由 ADR 给出） |
| R9 运费退还 | 见 6.5.1 |

#### 6.5.1 运费退还判定

| 场景 | 运费处理 |
|---|---|
| 未发货整单取消/退款 | 全额退运费 |
| 商家责任 · 整单所有组均退款 | 全额退运费 |
| 商家责任 · **部分组**退款 | 只退该组的内部运费份额 `freight_share`；后续组再退时，只有"全部组均已退"或"剩余组不再发货"才补退剩余，**累计退运费 ≤ 用户实付运费** |
| 用户无理由退货 | 退商品实付额，不退运费 |
| 部分数量退货（用户责任） | 不退运费 |
| 部分数量退货（商家责任） | 按该组 `freight_share` 退，规则同上 |

> "全额退运费"的准确含义：**整单场景**指用户实付运费全额；**部分组场景**只退该组份额。任何情形下累计已退运费不得超过用户实付运费（INV-21）。`PLATFORM` 责任视同商家责任（见 6.5.3）。

> 该表为**默认业务口径**，见第 11 节 D-03，甲方可改；改动必须同时改 AC-14。表中"商家责任/承运商责任"由谁判定、何时判定、依据什么，见 6.5.2。

#### 6.5.2 责任判定（谁、何时、依据什么）

**责任方枚举（全局唯一，禁止同义扩展）**：`MERCHANT_WAREHOUSE`（商家仓）/ `CARRIER`（承运商）/ `CUSTOMER`（用户）/ `PLATFORM`（平台或系统缺陷）/ `UNDETERMINED`（未判定）。

**判定人**：只有客服有权作最终判定。系统只允许在下列"无需判断"的场景自动落值，其余一律 `UNDETERMINED` 等人工。

| 场景 | 自动责任 | 依据来源 |
|---|---|---|
| 未发货整单取消/退款 | `MERCHANT_WAREHOUSE` | 无履约发生（系统事实） |
| 支付后缺货（6.6） | `MERCHANT_WAREHOUSE` | 系统事实 |
| 用户主动无理由退货 | `CUSTOMER` | 用户自述 + 法定期限 |
| 承运商回传丢失/破损 | **不落值**，只生成 `CARRIER` 建议 | 必须客服核对运单与轨迹后确认 |
| 拒收、错发、少发、地址问题 | `UNDETERMINED` | 必须人工 |

**判定输入（缺一不可，全部结构化）**：责任方枚举、判定来源（系统自动 / 客服 / 承运商证据）、证据引用（运单号、轨迹节点、照片编号）、判定人、判定时间、原因码（枚举）。

**自由文本 `reason` 不得作为判责依据**，更不得由文本关键字推导责任（INV-29）。

**时点**：售后受理之后、运费结算之前；商品退款不等判定。

**运费挂起规则（强制）**

1. 商品退款**不被**运费判定阻塞：责任为 `UNDETERMINED` 时，商品部分按 6.5、6.5.1 照常退款。
2. 运费部分进入"待判定挂起"，上限 **168 小时（7 天）**；判定后按 6.5.1 补退或确认不退。
3. 超 168 小时仍未判定：**默认按 `MERCHANT_WAREHOUSE` 补退运费**。"拖着不判"不得成为商家少退的理由。
4. 挂起期间用户必须能看到"运费待判定"及最长时限，不得显示为"已结清"。

#### 6.5.3 责任原因码与证据（最小集，枚举封闭）

| 责任方 | reason_code（枚举） | 必填证据 |
|---|---|---|
| `MERCHANT_WAREHOUSE` | `OUT_OF_STOCK` / `WRONG_ITEM` / `MISSING_ITEM` / `DAMAGED_PACKAGING` / `LATE_DISPATCH` | 缺货记录 / 出库单与实物比对 / 包装照片编号 |
| `CARRIER` | `LOST_IN_TRANSIT` / `DAMAGED_IN_TRANSIT` / `WRONG_DELIVERY` | 运单号 + 轨迹节点 + 承运商回单 |
| `CUSTOMER` | `NO_REASON_RETURN` / `REFUSED` / `ADDRESS_ERROR` | 用户申请记录 + 签收/拒收轨迹 |
| `PLATFORM` | `SYSTEM_DEFECT` / `PRICING_ERROR` | 缺陷单号或审计记录 |
| `UNDETERMINED` | `PENDING_REVIEW` | 无（等待人工） |

- 枚举封闭：**不允许 `OTHER`**；新增原因码必须升版 Spec。`PLATFORM` 视同商家责任：全额退运费（整单）或退该组份额（部分组）。
- 承运商/系统的"建议值"不得直接落为最终责任，必须经客服确认（6.5.2）。

**无授权超退**：`INV-24` 是硬约束，任何角色、任何理由（含客诉安抚）都不得突破"行剩余可退额"与"订单 captured 剩余"。确需超额补偿的，走独立的平台补偿通道，**不得混入订单退款**；该通道本期不做（D-10）。

### 6.6 缺货与库存变化

| 时点 | 规则 |
|---|---|
| 付款前预览 | 分配是"报价事实"，不是预留；下单瞬间重新校验。库存变化导致原方案不可行时，**必须在同一响应内返回重算后的完整新方案**（新的拆单结构、行金额、优惠、运费），由用户确认；不得只返回"请重新预览"让调用方再发一次，也**不得静默换仓或静默改运费** |
| 付款前下单校验失败 | 明确返回"库存已变化"并附新预览；用户不接受则下单失败，不扣款 |
| 付款后、发货前发现仓内实物不足 | **禁止**换仓/加组/降级；系统必须在**缺货确认后 4 小时内**（系统计时，起点=该组进入缺货待处理）自动通知用户，二选一：等待补货（给出明确日期）或该组退款；用户自**通知发出后 48 小时**内未选择，默认该组退款（fail-safe，不扣用户）。4 小时是系统计时口径，不是人工 SLA |
| 发货后发现少发 | **本期只做该部分退款，不做补发**（D-09）；不得跨仓调拨 |
| 已支付订单 | **仍计划履约的组**不得出现"预留已释放且仍可继续发货"的状态组合（基线 INV-06）；已进入组级退款（`refund_state=REFUNDING/REFUNDED`）且许可已 `REVOKED`/运单已 `CANCELLED` 的组，其预留由退款准入释放或补偿释放，是合法结果，不构成该禁止组合 |

#### 6.6.1 组退款后的库存处置

- 组退款来源包括：普通售后退款、TCC 补偿退款、SYSTEM 缺货退款；三者共用同一组级退款准入。
- 未离仓组（无运单 / 运单 `CREATED` / `CANCELLED`）：由 Inventory 释放该组预留；`HELD` 直接释放，`CONFIRMED` 走基线 `CancelConfirm` 的补偿释放。
- 上述“无运单”不含“许可 `CONSUMED` 且无运单”的异常状态；后者由 AC-50 写路径返回 `REFUND_ADMISSION_CONFLICT` 并告警（不属于 AC-27A 读模型谓词），不得按本条释放或关闭，须按 §16.2 `AC-27-NOWB-01` 人工核对。
- 已离仓组（运单 `SHIPPED/RECEIVED` 或带离仓时间的 `EXCEPTION`）：不得释放预留来“冲销”已发事实；退货回库仍按 INV-03，回库成功后再退款。
- 释放/回库失败必须重试并告警；释放后 `available <= on_hand`，且行数量守恒（INV-17），不得超卖或重复退款。
- 组退款不改变订单生命周期；退款进度只写 `refund_state`，不得写回 `orders.status`（INV-01/AC-25）。
- 上述限制只约束持久化 `orders.status` 与退款态写入；S2 读模型履约投影 `shipment_status` 按 §7.5/AC-27A 聚合已关闭组，不属于“写回 `orders.status`”。不得把 `shipment_status=SHIPPED` 误读为持久化生命周期已推进。

### 6.7 取消与退款边界

- 未支付：整单取消，所有组释放。
- 已支付未发货：**不提供"取消"语义**，只能按组退款；退款完成或 AC-27A 关闭谓词满足后，该组呈现"已关闭"，但不写订单生命周期。
- 组关闭按 AC-27A 判定（含 pre-ship `REFUNDING` 的许可/运单终态）；关闭后该组不计入 S2 履约投影的“剩余组”，关闭本身不写 `orders.status`，退款进度仍只由 `refund_state` 表达。
- 部分发货：已发组只能走售后；未发组走退款；订单**不得整体取消**。
- 全部组均已退款且未发货：订单对外展示"已关闭（全部退款）"，由 S1+S4 推导，不落生命周期值（INV 铁律 1）。
- 拆除/退款不得回滚已消耗的优惠额度；优惠额度按实际退款比例释放，释放值不得大于已占用值。

### 6.8 承运商、轨迹与签收

**承运商**
- 承运商为**受控清单**（甲方批准后启用），不允许自由文本；未登记的承运商不得发货。
- 运单号必填；同一承运商下运单号唯一，重复即视为疑似错单，阻断发货并告警。
- 换承运商/换运单号：**仅 Admin 可操作**，必须填 `change_reason` 枚举（`WRONG_CARRIER` / `WRONG_TRACKING` / `CARRIER_SWITCH` / `RELABEL` / `OTHER`，`OTHER` 必填备注），且只能发生在"未发货"或"已作废"的运单上；用户端不可修改运单。

**轨迹状态**（只能前进，不能回退，除争议覆盖）

```text
CREATED → SHIPPED(已揽收) → IN_TRANSIT(运输中) → OUT_FOR_DELIVERY(派送中) → DELIVERED(已签收)
                     └──────────────┴──────────────┴──> EXCEPTION(拒收/退回/丢失/破损)
```

- 轨迹事件重复到达：幂等，不改变已达成的最远状态。
- 轨迹乱序到达：只接受"比当前更远"的状态；`DELIVERED` 之后不得被任何非争议事件拉回（INV-25）。
- 异常轨迹进入"待处理"，由客服按判责矩阵判定责任后**走售后退款**（本期不做补发）；**异常不自动触发退款**。

**签收与收货**
- 签收事实来源只有两个：承运商 `DELIVERED` 事件、用户在订单详情主动确认（S7）。
- 签收后进入"待确认收货"：用户可在**签收事件时刻起 24 小时**内申诉"未收到"；申诉即转"争议中"，冻结自动确认，客服须在 **3 个工作日**内给出结论并留痕。
- 无申诉时，**签收时刻起 24 小时**自动确认收货（T+1 与申诉窗口为同一时点）。
- **申诉优先于自动确认**：申诉在自动确认生效前到达即取消自动确认；两者在同一时刻到达，按"申诉成立"处理（fail-safe 偏向用户）。
- 完全没有轨迹的订单：**发货时刻起 168 小时**自动确认收货；自动确认前必须在订单详情至少提示一次，文案统一为"**已自动确认收货（无物流轨迹）**"，**绝不显示"已签收"**。
- 已自动确认后用户仍可发起"未收到"争议（自动确认后 **15 天内**），但**不回滚收货事实**：只追加争议标记并进入售后/裁决流程，裁决成立后按 6.5 退款。
- 客服**不得**直接改签收或收货状态；只允许发起"争议裁决"动作，且必须填写依据。

**计时口径**：系统自动任务一律以**小时**为单位（4h / 24h / 48h / 168h），起点分别为缺货确认时刻、签收事件时刻、通知发出时刻、发货时刻；面向用户的长期窗口（争议救济 15 天、历史承运商补录 30 天）按**自然日**计，结束于第 N 天 23:59:59（Asia/Shanghai）。

**退货物流**
- 用户寄回时必须填写退货承运商与运单号（现有 `return_carrier/return_tracking_no` 语义沿用），承运转为受控清单。
- **历史自由文本承运商**：按映射表转为 code；无法识别的统一记 `UNKNOWN` 并进入"待补录"清单（30 天内人工补录），**不得阻断退货与退款流程**。
- 退货签收不直接触发退款：必须先完成回库（S11=`DONE`），再进入退款（基线 INV-03）。
- 退货丢件/破损由客服按判责矩阵处理，不得由用户承担非用户责任的损失。

**判责矩阵（入口；本期处理方式只有"退款"，无补发）**

| 情形 | 默认判责 | 处理入口 |
|---|---|---|
| 运输中丢失 | 承运商 | 部分/全额退款 + 承运商索赔（不补发） |
| 运输中破损 | 承运商（包装责任另判仓库） | 退货退款（不补发） |
| 错发/漏发 | 仓库 | 部分退款（不补发） |
| 用户拒收 | 用户（除非错发/破损/超时） | 退货退款，运费按 6.5.1 |
| 地址错误/无人签收退回 | 用户 | 退货退款，运费按 6.5.1 |
| 平台/系统缺陷导致 | `PLATFORM` | 视同商家责任：退款并按 6.5.1 退运费 |

### 6.9 用户可见性与知情

- **付款前**：结算页必须显示"本单将分 N 个包裹、来自 N 个仓"，以及一行订单级运费；不得只显示总价而不提拆单。
- **付款后**：订单详情必须按组展示"仓库 → 包裹 → 物流状态"，用户能分别看到每个包裹到哪一步。
- **缺货/延迟**：任一组进入 6.6 的缺货流程时，订单详情必须显著提示，且给出"等待/退款"的可选操作。
- **售后**：必须展示按行计算的可退数量与可退金额，用户只需选数量，不需要也不允许自己算钱。
- **自动确认收货**：必须显示确认原因（有签收事件 / 无物流轨迹超时），不得笼统写"已签收"（AC-37）。
- **费用明细**：运费减免（运费券）、运费待判定、运费补退必须分别可见，不得合并成一个数字掩盖差异。

## 7. 状态机

### 7.1 订单生命周期（不变）

```text
PENDING_PAYMENT --支付确认--> PAID --首组运单创建（发货授权）--> ALLOCATED --全部发货--> SHIPPED --全部收货--> COMPLETED
       │
       └──取消/超时/结算失败退款──> CANCELLED
（仅 PENDING_PAYMENT 可取消；PAID 后不提供用户取消；TCC 补偿/结算失败可进入 CANCELLED，见 §6.7）
```

> 本图描述持久化 `orders.status`（S1）：`PAID→ALLOCATED` 由首组运单创建（发货授权）触发；`ALLOCATED→SHIPPED`/`COMPLETED` 由真实发货/收货事实触发；取消由整单取消/结算失败事实触发。组关闭/退款完成不写入本图；S2 读模型 `shipment_status` 按 §7.5/AC-27A 单独表达。已关闭组不参与“剩余组”聚合，但本图的 `全部发货` 仍由真实发货事件触发，不得由退款完成触发。

### 7.2 履约组

```text
PENDING --支付--> ALLOCATED --运单创建/发货--> SHIPPED --签收/确认--> RECEIVED
   │                  │
   └──整单取消────────┴──> CANCELLED（持久化 S3，仅整单取消写入）
                         └──退款撤许可/AC-27A 关闭谓词──> CANCELLED（读模型派生；不改 S3）
```

> 持久化 `CANCELLED` 只由整单取消写入；退款撤许可只改 S5（许可），不改 S3。读模型可把 AC-27A 关闭组展示为 `CANCELLED`（派生值），但不得回写持久化 S3。

### 7.3 组退款态（正交，不得并入 7.1/7.2）

```text
NONE --进入退款--> REFUNDING --退款完成--> REFUNDED
```

### 7.4 运单 + 轨迹

```text
CREATED --发货--> SHIPPED --签收--> RECEIVED
   │                  │
   └─组退款作废─> CANCELLED
                      └─异常轨迹─> EXCEPTION（不影响运单状态，只影响物流展示与判责）
```

### 7.5 拆量订单的组合投影（只读结论，不新增状态）

| 场景 | 生命周期（`orders.status`，持久化 S1） | 履约投影（`shipment_status`，读模型 S2） | 组 | 退款态 |
|---|---|---|---|---|
| 2 组均未发、未创建运单 | PAID | UNSHIPPED | ALLOCATED×2 | NONE |
| 2 组均未发、已创建运单 | ALLOCATED | UNSHIPPED | ALLOCATED×2 | NONE |
| G1 已发、G2 未发（未关闭，仍计划履约） | ALLOCATED | PARTIALLY_SHIPPED | G1 SHIPPED / G2 ALLOCATED | NONE |
| 全发 | SHIPPED | SHIPPED | SHIPPED×2 | NONE |
| G1 收货 | SHIPPED | PARTIALLY_RECEIVED | G1 RECEIVED | NONE |
| 全收 | COMPLETED | RECEIVED | RECEIVED×2 | NONE |
| G2 退款中（未发，已关闭） | ALLOCATED | SHIPPED | G1 SHIPPED / G2 CANCELLED | G2 REFUNDING |
| G2 退款完成（未发，已关闭） | ALLOCATED | SHIPPED | G1 SHIPPED / G2 CANCELLED | G2 REFUNDED |
| G2 退款完成、G1 未发且未关闭 | PAID/ALLOCATED（取决于 G1 是否已创建运单） | UNSHIPPED | G1 ALLOCATED / G2 CANCELLED | G2 REFUNDED |
| 全部退款（未发，未创建运单） | PAID | UNSHIPPED | CANCELLED×2 | REFUNDED×2 |
| 全部退款（未发，已创建运单） | ALLOCATED | UNSHIPPED | CANCELLED×2 | REFUNDED×2 |
| 全部退款（未发）对外展示 | — | — | — | **"已关闭（全部退款）"，不写 status** |

> 注 1（读模型口径，v1.5）：生命周期列是持久化 S1；`PAID→ALLOCATED` 由首组运单创建（发货授权）触发，`SHIPPED`/`COMPLETED` 由真实发货/收货事实触发；G2 的关闭/退款完成不写入 `orders.status`（§6.6.1/AC-25/INV-01）。未创建运单的“未发”行为 `PAID`，已创建运单为 `ALLOCATED`。本表以 2 组为例；3 组按剩余组聚合，不得把仍有未关闭组的订单期望为 `SHIPPED`。AC-27 的 G2 退款行按“G1 先发货、G2 后关闭”的时序；若 G1 的发货事件在 G2 关闭之后才到达，`orders.status` 可由该真实发货事件按 §7.1 推进，不属于退款写入。
>
> 注 2：`G2 CANCELLED` 是读模型派生值（由组状态/许可/组退款准入结果派生），不是持久化组 `status`；持久化组 `status` 可以仍为 `ALLOCATED`，持久化 `CANCELLED` 只由整单取消写入。`G2 REFUNDING` 只表示退款仍在途，不等于退款完成；组退款态 `refund_state` 是 S4（SPEC-0002 编号 S9），不参与关闭谓词（AC-27A）。
>
> 注 3：G2 的预留是否已 `RELEASED` 由 Inventory 事实决定，不影响本表投影；`reservation_state=HELD` 不阻止关闭，不得由 Order 回写 `RELEASED`。多组订单当前不产生释放请求（P1/manual 已知缺口，台账登记）；AC-27/27A 不以 INV-44 完成为前提，释放证据归 Inventory 对账/台账，不得用 Order fixture 的 `RELEASED` 冒充；AC-27/27A PASS 不得反推 INV-44 已完成。G2 已关闭/已退款的组合按 §6.6/§6.6.1 合法，不构成 §6.6 的禁止组合。若出现组持久化 `CANCELLED` 与运单 `SHIPPED/RECEIVED` 并存，属数据异常，必须告警并人工核对，不得据此回滚履约（S6/S7）。
>
> 注 4：AC-26 适用于“G2 未发且未关闭（仍计划履约）”；AC-27/AC-27A 适用于“G2 已关闭”。同一组数据如 G2 已关闭，按 AC-27 判定，不得再套用 AC-26 的 `G2 ALLOCATED` 期望。

## 9. 验收标准（AC）

> 每条 AC 必须可由测试人员在不了解实现的前提下判定通过/失败。

### 拆量与选仓

**AC-01** 单仓可满足
Given SKU-A 在仓 1 有 5 件、仓 2 有 5 件，用户购买 3 件
When 结算预览并下单
Then 只有 1 条行、1 个组（G1/仓 1）、1 个包裹；运费 1 笔

**AC-02** 拆量成交（**无单仓可满足**）
Given SKU-A 在仓 1 有 2 件、仓 2 有 2 件（任一仓都不够 3 件），用户购买 3 件
When 结算预览
Then 展示"2 个包裹、来自 2 个仓"；行 = 2 条（仓 1 x2、仓 2 x1）；组 = G1/G2；行数量之和 = 3

> 反向判据（A-01 裁决）：只要**任一仓**可单独满足 3 件，就必须按 §6.1 不拆量，返回 1 条行 1 个组。若实现为"2 仓各 2 件却拆量"或"仓 2 有 5 件却拆量"，均判 AC-02 FAIL。

**AC-03** 拆量不改价
Given AC-02 场景，SKU-A 单价 1000 分，订单有 500 分优惠
Then 两行单价均为 1000 分；Σ 行优惠 = 500 分；Σ 行实付 + 运费 = 用户应付

**AC-04** 运费只收一次
Given 两仓各 2 件，用户买 4 件，商品金额未达包邮门槛
Then 用户应付中的运费 = 10 元（1 笔），不是 20 元；各组内部运费分摊之和 = 10 元

**AC-05** 包邮门槛按单判定
Given 商品金额 99 元拆成 2 组，单组均低于门槛
Then 用户运费 = 0（按订单合计判定），不得向用户收取 2 笔运费

**AC-06** 总量不足
Given 两仓合计 2 件，用户购买 3 件
Then 下单被拒绝，提示"最多可买 2 件"；不得创建订单

**AC-07** 拆量上限
Given 需要 3 个仓才能满足
Then 拒绝，提示建议减少数量或分单；不得创建 3 组订单

**AC-08** 并发抢最后一件
Given 仓 1 剩 1 件，两个用户同时下单 1 件
Then 恰好 1 人成功；另一人收到"库存已变化"并可重新预览；库存不为负

**AC-09** 支付后不重分配
Given 拆量订单已支付
When 仓 1 后续缺货
Then 组/行/仓快照不变；不得自动换到仓 2

### 金额与售后

**AC-10** 行实付单价与逐次退款
Given 行实付额 1000 分、数量 3（单价 333 分，末次补差）
When 用户先退 1 件、再退 2 件
Then 第一次退 333 分、第二次退 667 分；两次合计 = 1000 分

**AC-11** 退款额不可自填
When 调用任意入口发起售后并附带金额
Then 系统按规则计算并展示，申请金额不影响退款结果；展示值与最终打款一致

**AC-12** 双层额度校验
Given 行剩余可退 500 分、订单 captured 剩余 300 分
Then 本次最多退 300 分；超出被拒绝

**AC-13** 跨仓同 SKU 分开退
Given SKU-A 有仓 1、仓 2 两条行
When 对仓 1 行退 1 件
Then 只有仓 1 行额度减少；仓 2 行额度不变；不得合并退款

**AC-14** 运费退还判定
Given 6.5.1 六种场景各一单（未发货取消 / 商家责任整单 / 商家责任部分组 / 用户无理由 / 部分退货用户责任 / `PLATFORM` 责任）
Then 退运费金额与 6.5.1 一致；部分组场景只退该组 `freight_share`；任何场景累计已退运费不超过用户实付运费

**AC-15** 回库先于退款
Given 退货已签收但回库未完成
Then 退款保持阻断，用户看到的组状态为"待回库"

**AC-16** 回库归属
Given G2 从仓 2 发出
When 用户退货并被签收
Then 回库发生在仓 2；不得回仓 1

### 承运商与签收

**AC-17** 承运商受控
When 发货使用未登记承运商
Then 发货被拒绝并提示可选承运商

**AC-18** 运单号唯一
Given 已有订单使用承运商 X + 运单号 N
When 另一订单使用同一组合
Then 发货被阻断并告警

**AC-19** 轨迹单调
Given 已收到 DELIVERED
When 之后到达一条 IN_TRANSIT
Then 状态仍为已签收；展示不回退

**AC-20** 签收自动确认
Given 包裹 DELIVERED 且用户在签收后 24 小时内未申诉
Then 签收后 24 小时自动确认收货（与申诉窗口同一时点）；组 = RECEIVED；订单投影相应推进

**AC-21** 无轨迹自动确认
Given 发货后 168 小时（7 天）无任何轨迹、无申诉
Then 自动确认收货；此前订单详情至少提示过 1 次

**AC-22** 签收争议
Given 用户对 DELIVERED 申诉未收到
Then 状态转争议中、冻结自动确认；客服 3 工作日内给出结论并留痕

**AC-23** 客服不可改签收
When 客服尝试直接把签收置为真
Then 操作被拒绝；只能提交争议裁决

**AC-24** 异常轨迹不自动退款
Given 轨迹为"丢失"
Then 进入待处理；客服裁决前不得自动退款或自动补发（本期无补发能力，见 D-09）

### 状态与投影

**AC-25** 生命周期不含退款态
Given 任意退款场景
Then 订单生命周期只会是 7.1 的 6 个值；"全部退款"只能作为展示结论

**AC-26** 组级投影
Given 2 组订单，G1 发货、G2 未发
Then 生命周期 ALLOCATED、履约投影 PARTIALLY_SHIPPED、G1 SHIPPED、G2 ALLOCATED

**AC-27** 已退款/已关闭未发组不卡住订单（v1.5 读模型口径）
- WHEN 拆量订单的 G2 已关闭（按 AC-27A；`refund_state` 可为 `NONE`/`REFUNDING`/`REFUNDED`）且 G1 正常发货，
  THE SYSTEM SHALL 使 S2 读模型履约投影 `shipment_status` 按剩余组（排除已关闭组）的实际发货/收货进度聚合；
  仅当除 G1 外其余组均已关闭（无其他未关闭组；例如 2 组订单）时，仅剩 G1 且 G1 已发货、尚未收货时，
  `shipment_status` SHALL 为 `SHIPPED`，不得停留在 `PARTIALLY_SHIPPED`/`UNSHIPPED`；G1 已收货时 SHALL 为 `RECEIVED`；
  G2 不得阻塞 G1 发货。IF 仍有其他未关闭组（如 3 组订单的 G3），THEN SHALL 按实际剩余组聚合
  （例如 `PARTIALLY_SHIPPED`），不得错误期望 `SHIPPED`。
- WHILE G2 已关闭（按 AC-27A），THE SYSTEM SHALL 保持持久化 `orders.status` 为其既有合法生命周期值
  （`PAID`/`ALLOCATED`/`SHIPPED`/`COMPLETED`/`CANCELLED` 中其既有值；`PENDING_PAYMENT` 不适用——
  AC-51/AC-65 在组准入前已 CAS 到 `CANCELLED`；后续由运单创建/发货/收货/取消事实推进不受本条限制），
  并只通过 `refund_state`（S4；SPEC-0002 编号 S9）表达 G2 的退款进度；THE SYSTEM SHALL NOT 因 G2 的关闭或退款完成写入
  `orders.status`，也不得写入 `REFUNDING`/`REFUNDED`/`CLOSED` 等退款态（§6.6.1/AC-25/INV-01）。
- WHEN 未支付取消或 AC-51/AC-65 的 TCC 已捕获路径先把订单 CAS 为 `CANCELLED` 后再发生组关闭，
  THE SYSTEM SHALL 允许 `orders.status=CANCELLED` 与组关闭共存，并保持 `CANCELLED`；不得因组关闭把
  `CANCELLED` 改写为其他生命周期值，也不得写入退款态。
- WHEN Inventory 已确认 G2 的预留释放，或 Fulfillment 已确认 G2 的运单取消（本 Spec 不要求 Order 观测/断言这些事实），
  THE SYSTEM SHALL 按 §6.6/§6.6.1 判定该组合合法，不构成 §6.6 的禁止组合；该判定是规范层面的合法性结论，
  不是 Order 读模型的可观察性要求；释放证据归 Inventory，运单证据归 Fulfillment。AC-27A 的关闭谓词不使用
  `reservation_state` 或运单事实作为输入。
- WHEN 同一测试数据中的 G2 仍为 `ALLOCATED` 且未关闭（仍计划履约），THE SYSTEM SHALL 按 AC-26 处理
  （生命周期 `ALLOCATED`、履约投影 `PARTIALLY_SHIPPED`、G2 `ALLOCATED`）；AC-26 与 AC-27 的
  适用边界是“G2 是否已关闭”，不是“G2 是否未发”。

**AC-27A** 未离仓组的关闭谓词（pre-ship，EARS；新增子编号，不重编号既有 AC）
- WHEN 订单读模型判定某履约组是否“已关闭”（该组不会再产生包裹），THE SYSTEM SHALL 按以下固定顺序判定，
  且只使用 Order 自有持久事实（组投影状态、许可、组退款准入结果（RefundAdmission，owner=Order））：
  1. 组不存在 → 未关闭；
  2. 组持久化状态 = `CANCELLED` → 已关闭（持久化 `CANCELLED` 只由整单取消写入；退款撤许可只改 S5，不写 S3）；
  3. 组持久化状态 ∈ {`SHIPPED`,`RECEIVED`} → 未关闭（离仓守卫；先于任何许可/退款事实）；
  4. 许可 = `REVOKED` → 已关闭（AC-50 `NONE→REVOKED` 终态，INV-45；`refund_state`（S4；SPEC-0002 S9）不参与，`NONE/REFUNDING/REFUNDED` 均不改变此结论）；
  5. 许可 = `CONSUMED` 且组退款准入结果 = `PRE_SHIP_REVOKED` → 已关闭（`refund_state` 不参与）；组退款准入结果是唯一持久载体（见本节末“证据载体与前置缺陷”），不得以运单事实或 `state` 代替；
  6. 其他（含许可 `NONE`、组退款准入尚未收敛（`state=PENDING_REMOTE`）、`POST_SHIP_ALLOWED`、准入结果缺失/不可核验）→ 未关闭。
- IF 许可 = `CONSUMED` 且组退款准入结果不是 `PRE_SHIP_REVOKED`（含缺失、`state=PENDING_REMOTE`、取消/探测结果未知），
  THEN THE SYSTEM SHALL 保持该组未关闭并告警；不得要求 Order 读取/反推运单事实，不得在 AC-27A 读模型路径输出 AC-50 的写路径错误码。
- IF 已关闭组随后出现 `SHIPPED/RECEIVED` 事实（含迟到/重复事件），THEN THE SYSTEM SHALL 先按第 3 条离仓守卫处理：
  仅当该事实由 Order 的 S3 组投影收到 `shipment.shipped`/`shipment.received` 事件确认真实离仓时，
  才允许读模型转为未关闭并告警（owner=Developer（Order 数据核对）/Fulfillment（S6 证据）；本 Spec 不要求 Order 直读运单表）；
  该处理 SHALL NOT 改写已持久化的 `PRE_SHIP_REVOKED` 准入结果或许可终态：已打款按已离仓售后/对账处理，
  未打款按新 `refund_id` 重新准入 `POST_SHIP_ALLOWED` 并保留原 PRE 审计；重复事件幂等；
  无法判定（含重复/乱序/无事件证据）时转 §16.2 `AC-27-NOWB-01` 人工队列，不得把已关闭组重新打开，不得回滚收货事实。
- IF 触发组退款完成的事件在 DLQ、发起方 AfterSales durable task 租约丢失或 AC-61 人工重放后仍无法收敛，
  THEN THE SYSTEM SHALL 告警并提供 AC-61 的人工重放入口；owner=ops（重放）/Developer（AfterSales durable task 重试）；
  人工处置前保持该组未关闭，不得写 PRE、不得关闭、不得打款。
- WHILE `refund_state`（S4；SPEC-0002 S9）为 `NONE`/`REFUNDING`/`REFUNDED`，THE SYSTEM SHALL 只用它表达退款进度；
  它不参与关闭谓词，三者均不改变第 4/5 条的关闭结论；pre-ship `REFUNDING` 不阻止已满足第 4/5 条的组关闭，
  但不得把 `REFUNDING` 展示为“退款完成”。
- WHEN 判定关闭，THE SYSTEM SHALL NOT 以 `reservation_state` 作为关闭依据；`reservation_state=RELEASED`
  不是关闭的充分或必要条件，`HELD` 不阻止关闭；释放事实归 Inventory（INV-44），Order 不得写 `RELEASED`。
- WHEN 判定关闭，THE SYSTEM SHALL 只使用 Order 自有的许可/组退款准入/组投影事实；运单/签收事实归 Fulfillment（S6），
  Order 不得制造、回写或据以反推运单状态；运单 `CANCELLED` 只通过组退款准入结果代理进入。
- WHEN 组已关闭，THE SYSTEM SHALL 只把它从 S2 履约投影的“剩余组”中排除，并保留 `orders.status`
  的既有生命周期值；不得因关闭写入退款态。

> **证据载体与前置缺陷（AC-27A 注，不是新 AC）**：组退款准入结果的唯一持久载体见 §16 V15-2（`order_refund_admissions.result`）；AC-27A 正文只使用业务事实。`result` 只允许 `PRE_SHIP_REVOKED`/`POST_SHIP_ALLOWED`，`state=PENDING_REMOTE` 是中间态、不等同于 PRE。`CONSUMED+无运单` 的写路径规则与修复前置见 §16.2 `AC-50-FIX-01`；未修前 AC-27 不得 AC-VERIFIED；存量无法证明由 AC-50 合法分支写入的 PRE 按 §16.2 `AC-27-NOWB-01` 一次性审计，审计结论未出前台账不得把该组标为已关闭/AC-VERIFIED，读模型告警。
