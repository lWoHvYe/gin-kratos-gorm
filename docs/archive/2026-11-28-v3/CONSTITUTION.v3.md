# 项目宪法 v3.0

> 2026-11-28 v3.0 已合并到 main（人类方向）；独立 review pending；release_status: NOT RELEASE。只写原则与附录，操作细节在 AGENTS.md。

## I. 契约与变更

1. **行为变更先有 Spec。** 新增或修改行为/AC，必须先写 Spec，经独立审查、人类批准后才能实现。实现变更按已批准 Spec 执行。
2. **bugfix 不设特殊路由。** 已有行为被破坏、且已被批准 Spec 覆盖、且不触及契约主题时，按实现变更处理；否则按契约变更处理。不得用“bug”名义绕过 Spec/ADR。契约主题 = 新增/修改行为或 AC，或命中附录 B。
3. **ADR 与修订。** 跨服务协议/事件、数据模型/迁移、状态机、并发控制方案、技术选型必须写 ADR；ADR 与 Spec 同批审查、同批批准。已批准 Spec/ADR 不得静默改写；要变就升版或写新 ADR 取代，并重新批准。Spec 写业务/AC，机制写 ADR；plan 只承载不需要 ADR 的局部设计。核心交易链路重构不得 Break Change；用双写/版本化事件/影子消费，并写收口、移除日期、回滚。
4. **Spec 权威。** 一份业务能力只有一份权威 Spec；状态只在权威 Spec 的验收状态表。所有 active Spec 在 `specs/<id>/spec.md`；`specs/README.md` 是唯一 index；`docs/specs/` 只做重定向；不得同时维护两份权威。0001 为 historical reference（QC delta 待复审），0002 为 active；sdd-struct-align-01 为 historical。
5. **状态唯一来源。** 验收状态只在权威 Spec 的验收状态表；运行状态（裁决、冻结、批准、Release）只在 `docs/review-tracking.md`。plan/tasks/汇总文档不保存状态；任务勾选只是执行进度。0001 为 historical reference（QC delta 待复审；不再新增/改 AC；§17 表为历史状态）；0002 的 AC 状态以 §15 为准。

## II. 独立审查

6. **审查者不是作者。** 审查者必须是另一个 agent 实例，不参与被审变更的写作；只依据 Spec/ADR、精确 base/head 的代码、plan 与测试日志，不依据作者自述。能复跑必须复跑；不能复跑须写明原因、未覆盖范围并取得人类书面豁免。
7. **问题可溯源。** 每条阻断必须指向 AC、领域不变量、已批准 ADR、Spec 必备章节或本宪法条款；摘不到的记 `[TODO]`，不阻断。权限、安全、数据完整性、迁移、资金、库存风险必须阻断。审查者之外的其他输入只作问题提案，必须引用当前 HEAD，不能直接成为契约/AC/阻断依据。
8. **不给补丁、不替作者设计。** 审查者只指出违反项；设计缺陷回 Spec/ADR；不得建议“加锁/加 if”式局部修补。
9. **一次给全、有界升级。** 审查者同一轮列全 blocking 问题；作者一次修完，只复跑失败项+diff。超过 2 轮不收敛，由人类按“实现错误/证据不足/设计问题/契约缺口/环境”分类决定；不自动放行，高风险阻断不受轮次影响。
10. **PASS 与 AC。** 实现 PASS 不等于 Spec 全量验收，也不等于 Release；SCOPED-PASS 只表示声明范围证据满足，必须列未覆盖 AC/路径。AC 状态只由审查者写；作者不得自标 `[x]`。

## III. 证据

11. **口头 done 无效。** 行为变更必须附实际执行日志，绑定精确 HEAD；纯文档不得声称测试通过。可能使其他 Spec 已验证 AC 失效的变更，必须列出 AC 与非回归证据，由审查者更新验收表。
12. **高风险证据。** 资金、库存、履约、权限、跨服务、迁移、状态机的变更必须有并发/故障注入或等价负例；不适用必须取得人类书面豁免。Mock 必须符合真实业务边界，至少一个异常分支。
13. **交付三件事与 oracle。** 每次交付写【测试范围】【未覆盖范围】【取舍】。不得用测试绿灯冒充 intent-level 验证；独立 oracle 指不依赖实现自述的验收来源（验收示例、公开契约/schema、领域不变量、稳定旧行为、外部 conformance、生产 trace）；没有独立 oracle 的 claim 只能标“未验证”。
14. **Fail-Closed。** 资金、库存、订单核心链路中未预期的异常、超时、配置缺失必须报错阻断或进入持久补偿；不得静默放行、吞异常、用 TODO/空实现掩盖核心逻辑，不得只做 happy path。必需依赖构造期必填、启动期 fail-fast；测试替身不得弱化生产守卫；请求路径不得 panic；启动配置/依赖缺失必须非零退出。
15. **不伪造。** 未审写 `Reviewed-by: pending`，不得冒充已审；不得用 hotfix/新 change_id/缩范围绕过 FAIL；不得改写审查者裁决或 AC 状态。

## IV. 人类裁决

16. **人类批准点。** 批准 Spec（含链接 ADR）、合入、Release；回答业务裁决题。人类不逐条核对语法/文字。
17. **作者不得自行决定。** 业务取舍、契约/状态所有权变更、架构缺陷交人类或回 Spec/ADR；范围内缺陷由作者修。豁免必须逐台账写范围、期限、受影响不变量；无期限无效。

## V. 流程修改

18. **流程变更先试点。** 修改本宪法/AGENTS/核心流程必须从最小增量开始，写明可验证收益与停止条件；无数据不把假设写成硬规则。非规范 checklists/guides 不是验收依据。
19. **不新增角色/状态。** 除非人类批准；优先用现有作者/审查者/人类三角色；状态只落 Spec 验收表与台账。

20. **变更治理（防过程膨胀）。**
    - 一个 change 只解决一个问题；不得把治理、契约、迁移、工具改造混在一个 change。
    - 草案不得写到 live；live 只放评审通过/人类批准的文本。
    - 同一问题 2 次 review FAIL 必须停止，分类并重置；不得用第三版局部补丁继续。
    - 旧文本只作来源；先写 invariant map（保留/替换/退役/延后），不逐条兼容。
    - 大改先写目标/非目标/可验证指标；无指标不做流程重写。

## 附录 A：Spec 必备内容

| 必备问题 | 必须回答 |
|---|---|
| 业务规则与验收标准 | 每条 AC 可判定，能落到测试/契约检查/可观测指标；金额、状态、并发写拒绝错误；`SHALL`/`MUST` 后不得接无法判定的形容词。 |
| 状态所有权 | 每个核心状态字段唯一写入服务/表；不得把多个状态揉一个字段。 |
| 契约与异常恢复 | 幂等、最终一致性、持久恢复所有者；并发/超时/崩溃/部分成功/网络脑裂的预期行为；状态机无死胡同；协议/数据模型/状态机链接 ADR。 |
| 可达性检查 | 每条 AC 在现有代码的触发态，给 `文件:行号`；不可达标 `[不确定]`。 |
| 假设与不确定性 | 底层依赖风险。 |
| 业务裁决题 | 每题带编号选项；没有写“无”。 |
| 验收状态表 | AC 编号、状态（未验证/有引用/已验证/historical）、检查类型、证据路径、审查者。 |
| 延期清单 | AC/工作项、owner、expiry、reason；到期未关闭阻断对应范围；不得删行/批量续期/用新 change_id 规避。 |

## 附录 C：领域与安全不变量

C1. **幂等/事务/恢复。** 跨服务写必须以唯一约束或 CAS 兜底，不得只靠 Redis；跨服务调用必须有 Deadline/Timeout，重试退避并确认下游幂等。DTM Saga 走 `dtm.Branch`；业务写与 `outbox.Append` 共用 `*sql.Tx`；`gid` 确定性派生。跨服务资金/库存/履约写入必须有持久任务/工作流；外部重试/消息重放/崩溃不得作为唯一恢复。

C2. **事实与退款/履约准入。** `PaymentCaptured`、`OrderSettled`、`InventoryReady`、`FulfillmentAllowed` 是不同事实，不得由一个 status 或 `order.paid` 合并。普通售后、TCC 补偿、SYSTEM 退款必须同一组幂等准入，由 permit 裁决退款/发货竞态：
- 未完成退款且未授权发货：撤销/拒绝该组 permit；
- 已发货后退款：保留已发货事实，只退款，不回滚履约；
- `REVOKED` permit 不得由实现自行恢复；
- 准入前拒绝/取消不得创建 commitment；准入后失败必须持久重试/人工队列；
- TCC/SYSTEM 逐组准入，活动组金额之和等于剩余可退金额（Σ）；
- `order.paid` 只可作 BFF/旧消费者兼容，不得作为准入/结算/库存就绪依据；兼容期写切换、收口、移除日期、回滚。

C3. **读写/多仓/静态守卫。** `skus.stock` 是投影，真实库存在 inventory；必须 Read-Your-Writes。多仓操作/事件/恢复/replay 显式携带 `warehouse_id`；需要组身份的履约事件不得缺省 G1；未获 PRD 批准不得开启多仓。跨服务禁包引用；`internal/platform` 不依赖 `services`；事务核心用 `database/sql` + 条件 `UPDATE`；GORM 仅在 `catalog/gorm_repo.go`、`cart/gorm_repo.go` 读侧；对外错误用 `apperr`；不改生成物。

C4. **AI 与安全。** `ai` 故障不得影响浏览、下单、支付；AI 走统一 `Turn/Action`；写操作“草案→人工确认→RPC”；身份只来自服务端。AI 工具默认只读；Mesh 使用显式服务间 ALLOW 和 AI 精确只读 ALLOW，不得依赖 broad ALLOW 加不完整 DENY。RAG 必须版本化可变索引，不得原地重建。

C5. **技术栈与协议。** 不引入未批准技术栈；无测量不做极值优化；dev 压测 ≤100k/1M RPS；`main` 不新增半成品协议路径。
