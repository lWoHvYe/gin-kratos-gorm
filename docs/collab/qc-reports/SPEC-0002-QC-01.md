## 1. 结论

**BLOCKED。** v0.1 不能进入 `in-review`/`approved`，也不能交给 Architect 起草 ADR-0007，理由是：

1. **10 项 BLOCKER**，其中 7 项与已批准契约（SPEC-0001 v1.2、基线 INV-01…16）直接冲突：状态所有权、发货许可枚举、缺货二选一、签收事实所有者、取消语义、幂等与资金口径。
2. **资金口径自相矛盾**：AC-41 与 AC-44 对"第二笔捕获"给出相反裁决（行 126–127 vs 141–143）；§5 E8（行 226）把"多 intent 各自 captured"写成正常路径，与非目标"本期不做部分支付"（行 57）、INV-30（行 92）冲突。
3. **5 个必答崩溃窗口全部只有部分答案**（唯一例外是"重复投递"本身），且**全部缺"恢复所有者"**（见 §2），不满足 `prompt/Quality-Checker.md:11-19` 与 `AGENTS.md:34`。
4. **门禁事实**：草案一旦入库，G-3 会立即报 20 条 `AC-39…58 not in baseline`（`scripts/collab_gates.py:289`）并额外报 20 条 `no test, no valid deferral`（`:321-323`），strict 模式 exit=1（`:367-370`）；G-2 报 `not found in docs/specs/README.md`（`:198`）。

**放行未满足的硬条件**（不是修改建议，是判定条件）：所有 BLOCKER 关闭并与已批准条款对齐；五窗口逐条写出预期行为 + 恢复所有者；跨 Spec 冲突要么由人类批准升版修订被冲突条款并注明影响 INV/AC，要么在 SPEC-0002 内显式"遵从并引用"；AC 台账与索引同步（`CONVENTIONS.md:30`）。

## 2. 五个必答窗口逐条回答

### 2.1 窗口 1：本地提交后崩溃

- **已定义**：`spec:104`（INV-42 要求先持久化意图再执行）、`spec:137-138`（AC-43 捕获提交后崩溃 → 从持久意图继续）、`spec:220-221`（E2 捕获提交后崩溃、E3 本地提交 DTM 未受理）。
- **未定义的同类窗口（3 条）**：
  1. 售后退款意图已提交、未调用 Order 准入（`spec:173` 要求"先持久化退款意图，再向 Order 申请"，但没有任何 AC 或 E 行定义此崩溃点的恢复动作；E9 行 227 是反方向）。
  2. Order 已撤销许可、通知 Fulfillment 取消运单前崩溃（`spec:174` 是两段式动作，无崩溃语义）。
  3. 缺货案件已 `NOTIFIED`、通知用户前崩溃（`spec:200`/`spec:76`）。
- **恢复所有者**：全文未指名。§2 状态所有权表（`spec:67-76`）没有"结算意图/退款任务/通知任务"这一事实行，因此连"谁拥有恢复职责"都无法从所有权表推出。
- **判定**：缺口。违反 `prompt/Quality-Checker.md:15`（"谁驱动后续"）与 `AGENTS.md:80`（持久任务/工作流必须有驱动方）。

### 2.2 窗口 2：跨服务 RPC 成功后崩溃

- **已定义**：`spec:227`（E9：退款准入 RPC 成功、本地未提交 → "许可已变更，可重试"；撤销未发运单幂等）、`spec:141-143`（AC-44 回调重复）、`spec:222`（E4 结算 RPC 超时未知）、`spec:145-147`（AC-45 不得把更新失败当幂等成功）。
- **缺失**：
  1. 没有任何 AC（可执行条款）覆盖该窗口——E9 只是 §5 的一张表单元格，`spec:215` 未声明该表与 AC 的关系，`CONVENTIONS.md:114` 明确"线程里的临时结论不是契约"，矩阵同理需要规范性地位。
  2. "重试时如何判定上游已成功"的判据缺失：E9 只说"可重试"，未说重试读取哪个权威事实判定 `PRE_SHIP_REVOKED`/`POST_SHIP_ALLOWED`（`spec:73`）。这正是 triage 2.3 要求 ADR 定义的"幂等成功的判据"（`docs/ext-review-1123-triage.md:79`）。
  3. 幂等键（谁生成、作用域、重试语义）完全未声明；`architecture-baseline.md:332` 把该项列为 Spec 接收必覆盖清单第 7 项，`AGENTS.md:78` 要求 DB 唯一约束或状态机 CAS 兜底。
- **判定**：缺口（Q-14）。

### 2.3 窗口 3：消息重复/乱序

- **重复**：`spec:141-143`（AC-44 只产生一次结算副作用；不一致回调拒绝并告警）、`spec:219`（E1）、`spec:206`（AC-57 收货只一次）。**判定：已定义。**
- **乱序**：除 AC-44 的"重复投递"外无任何条款。具体未收敛的组合至少 5 个：
  - `payment.refunded` 先于 `payment.succeeded` 到达时，订单退款投影与 `SETTLED` 谁先生效（`spec:71` vs `spec:70`）；
  - `shipment.received` 先于 `shipment.shipped`；
  - `order.settled` 先于 `order.paid`；
  - Fulfillment 先收到 `FulfillmentAllowed` 再收到 `InventoryReady`（`spec:36` 四事实顺序）；
  - Order 先收到 `inventory.operation.failed` 再收到 `payment.succeeded`。
- **违反**：`architecture-baseline.md:331` 要求 Spec 覆盖"重复、乱序"等六类分支；`architecture-baseline.md:230` 已有单调投影防线但 0002 未引用、未复述；`AGENTS.md:34` 要求 QC 检查并发/超时/崩溃，但 PO 侧同样必须穷举。
- **判定**：缺口（Q-17）。

### 2.4 窗口 4：取消/确认竞态

- **已定义**：`spec:101`（INV-39 唯一胜者 + 败者退款/释放）、`spec:151-154`（AC-46）。
- **缺失/矛盾**：
  1. **胜负窗口未限定**：支付已捕获后是否允许"取消胜出"？`spec:139`/`spec:153` 允许"取消先提交 → 已捕获资金自动退款"，而 SPEC-0001 §6.7（`docs/specs/0001-...md:291-294`）规定"已支付未发货不提供取消语义，只能按组退款"。0002 未说明其"已支付"指 `SETTLED` 还是 `orders.status=PAID`，因此两条已批准/草案条款对同一场景结论相反（Q-11）。
  2. **"同一权威状态机"未指名**（`spec:152`）：是 `orders.status` CAS、`SETTLED` 字段，还是许可行（`architecture-baseline.md:202` INV-04）？不可判定，也无法写测试。
  3. **败者无可见结论**：AC-46 未给返回码，而同类 AC（AC-39/48/56/57）均给了错误码，违反"每条 AC 可由测试人员判定"（`docs/specs/0001-...md:436`）。
  4. **三方竞态缺失**：取消 × 退款准入 × 发货（含许可已消费、运单未 SHIPPED 的中间态）无定义。
  5. **已确认库存的回退**：若结算已 confirm 库存后 cancel 到达，`spec:153` 只写"库存与优惠不得确认"，未写已确认的释放/回库动作。
- **判定**：缺口（Q-11）。

### 2.5 窗口 5：外部重放缺失

- **已定义**：`spec:35`（钱一旦捕获系统自己负责送终态）、`spec:94`（INV-32）、`spec:138`（AC-43 不依赖渠道重放）、`spec:233`（E15）。
- **缺失**：
  1. 仅覆盖"捕获→结算"。**退款执行失败**（`spec:195` 只"保持可重试"）没有驱动方、没有重试预算、没有"永久失败"的业务终态，与 INV-32 要求的"系统自行到终态"不等价。
  2. **缺货 48h 默认退款**依赖定时任务，但 0002 未声明"系统自行计时"的归属与起点复述；SPEC-0001 §6.6 的 4 小时通知时限（`docs/specs/0001-...md:285`）在 0002 中缺失（Q-28）。
  3. **承运商永不回传轨迹**时，收货终态依赖 SPEC-0001 AC-21（168h 自动确认，`docs/specs/0001-...md:534-536`），0002 的 AC-57/58 未声明该跨 Spec 依赖是否继续有效。
  4. **渠道永久失败/拒付**（例如渠道侧关闭、二次扣款发生在本系统已退款之后）无业务终态裁决；D-12 只处理手续费（`spec:252`）。
- **判定**：缺口（Q-04/Q-14/Q-18/Q-28）。

## 7. 业务决策 vs 技术方案越权检查

### 7.1 PO 越权（把技术方案写成业务契约）

1. **S4 身份键**（`spec:72`）：`(order_no,line_no,sku,warehouse,quantity)` 是数据身份键，属表/幂等设计，且与基线 `(order_no,sku_id,warehouse_id)`（`architecture-baseline.md:74`）不一致 → 违反 `AGENTS.md:26`。要求：只声明事实粒度（订单/行/组），键交 ADR，但必须声明"与既有键兼容或升级"的业务约束。
2. **执行顺序**（`spec:104`、`spec:173`）："先持久化意图，再调用"是装配协议；`AGENTS.md:80` 已有铁律，Spec 重复它却不给所有者，导致既越权又不可验收（Q-25）。
3. **许可授予模型**（`spec:164` "请求发货许可"）：把 permit 写成 pull 模型，与既有"支付时授予、发货时消费"（`architecture-baseline.md:120-128`）冲突 → 属于技术模型变更，必须由 Architect 在 ADR 中提出，PO 只能声明业务约束（未就绪不得发）。
4. **D-14**（`spec:254`）：把"用户可见时限"这一业务承诺外推给 ADR/Ops → 反向越权（Q-26）。

### 7.2 技术细节缺失被误当业务问题

1. **D-15**（`spec:255`）：已发货组退款是否需要审批，SPEC-0001 S9/S10（`docs/specs/0001-...md:120-121`）与 P-06/R8 已裁决 → 不是开放业务问题，应引用或删除。
2. **INV-42 的"持久意图"**：业务上只能要求"钱不会丢、可自愈、可观测"；当前写法让读者以为恢复机制已被定义，但全文没有驱动方 → 技术缺口被 INV 措辞掩盖（Q-13）。
3. **`TERMINAL_FAILED`**（`spec:161`）：作为业务终态出现，但其判定条件（库存不足 vs 技术失败 vs 超时）本质是业务口径，被默认当成已解决；D-11 只决定了"动作"，没决定"判定" → 必须人类裁决（Q-02/Q-26）。

## 8. D-11…D-15 充分性与仍需人类裁决的业务口径

| 决策 | 评估 | 缺口 |
|---|---|---|
| D-11（`spec:251`） | **不充分且违规**：结论"组级自动退款"与已批准 INV-26/AC-30 的"显式通知 + 二选一"冲突；且未定义"永久失败"判定口径、未定义部分组失败时订单对外展示（`SETTLED` + 组退款） | 需人类二选一：修订 INV-26/AC-30，或在 0002 中恢复二选一流程（Q-02/Q-03/Q-04） |

## 9. 复审门禁（本报告判定"通过"的最低条件）

1. **契约冲突逐条处置**：C-1…C-8 每条要么在 SPEC-0002 内显式"遵循并引用"，要么由人类批准被冲突条款升版并在变更记录注明影响的 INV/AC（`CONVENTIONS.md:63`、`docs/specs/README.md:70-73`）；不得仅以 `spec:261` 的一般性声明覆盖。
2. **状态所有权收口**：§2 每个事实单一所有者、无聚合状态；S3/S4/S5/S6/S8 的迁移表与非法迁移语义齐备（`AGENTS.md:28`、`architecture-baseline.md:330`）。
3. **资金口径唯一**：订单级 captured/refunded 构成、生效支付判定、超付与重复支付的终态唯一且互不矛盾（`architecture-baseline.md:229`）。
4. **五窗口闭合**：每个窗口有可执行 AC + 恢复所有者 + 幂等判据；乱序单独成条（`architecture-baseline.md:331`）。
5. **EARS 可判定**：无"不可支付/可结算/最终/或"类模糊或二义；每条 AC 有唯一期望与返回码（`AGENTS.md:116-123`、`docs/specs/0001-...md:436`）。
6. **治理同步**：AC 台账（Reviewer 所有）与 `docs/specs/README.md`、`Spec.md` 索引、版本/变更记录同步；草案入库不得使 `make gates-strict` 变红（`CONVENTIONS.md:30`、`scripts/collab_gates.py:289/323`）。
7. **人类裁决落地**：§8 的 7 项业务口径有明确裁决与本 Spec 落点（`AGENTS.md:14`）。
