## 1. 结论

**PASS WITH CONDITIONS。** v1.6 把 TCC 补偿定义为**系统责任、每组全额**，并删除分摊与"订单级待退款"，实质性地消除了 N-66：

- AC-51 `:215` 每个活动组金额 = 系统责任上限（商品剩余 + **全部未退** `freight_share`）；`:222` 逐组全额打款，Σ 活动组上限**必须等于**订单剩余 `captured`，不等则阻断/告警/人工裁决、**不得部分打款**。
- AC-50 `:195` 明确 TCC 系统补偿的运费额度按"全部未退运费"计，因此 `整组退款金额 = 商品剩余 + 全部未退运费 = 系统责任上限`；`:197-198` 的未离仓金额门与 AC-51 的"每组全额"一致——原先"分摊额 < 组上限 → `PARTIAL_REFUND_REQUIRES_FULL_GROUP`"的冲突不再存在。
- N-67 的"订单级待退款差额"被删除，改为阻断；N-68 由 §5.3 `:329-330` 的"运费责任已定 + 挂起保持 `REFUNDING` + 后续判责属同一进度"收口；N-69 由 §5.5 `:359` 的 `DONE(zero_amount)` 注收口；N-70 由 AC-51 `:221` 的 G1 许可初始化收口。

因此无代码级 BLOCKER。剩余条件只有 **C-1/C-8/C-9**（人类/流程）；另有 4 项 ADR-0007 交接注意项（§4，不构成批准条件）。

## 3. 四个定向攻击的回答

| # | 攻击点 | 回答 |
|---|---|---|
| 1 | "Σ组上限=订单剩余 `captured`"在部分组已退款、运费已部分退、零元单、多组尾差下是否恒成立；不成立时阻断是否可执行 | **在 Spec 自身的组级退款流下恒成立，例外被阻断兜住。** 0001 INV-20/INV-21（`:146-147`）保证 Σ `freight_share` = 订单运费、Σ 行实付 + 运费 = 订单实付；INV-36 `:107` 要求普通售后/TCC/SYSTEM 三类退款都走组级准入，因此每笔退款同时减少组额度与订单 `refunded`，等式保持。逐项：①部分组已退款——该组剩余上限与订单剩余同时减少，等式保持；②运费已部分退——组未退运费与订单 refunded 同步，等式保持；③零元单——`captured=0`、各组上限 0，等式 0=0，`:220` 全组跳过、幂等成功；④多组尾差——不做分摊、无取整，整数上限求和即订单剩余。**例外**：订单级退款（AC-43 的取消全额退款）不被计入组额度，可能使 Σ 组上限 ≠ 订单剩余（此时剩余已为 0）→ `:222` 阻断、不支付、告警、转人工；**阻断可执行**（明确不部分打款、不标"待退款"），但人工裁决的 owner/动作需在 ADR-0007/ops 定义（C-9、R-1） |
| 2 | "系统责任上限含全部未退运费"与 0001 §6.5 运费责任/168h 挂起是否冲突 | **不冲突。** 0001 §6.5.2（`:257-262`）的 168h 挂起是"普通售后运费责任未定"时的暂缓规则，超时默认商家责任；0001 §6.5.3 已把 `PLATFORM`（系统/平台缺陷）视同商家责任。TCC 补偿是**系统责任**的独立退款来源（D-21 `:473`），退全部未退运费与 `PLATFORM` 口径一致。两套口径的交汇点：若某组运费责任仍挂起，§5.3 `:330` 要求该组保持 `REFUNDING`；TCC 在系统责任下可先退运费，后续判责不再产生第二笔（组额度已为 0，`REJECTED/CANCELLED`/额度门兜底）——需 ADR 确认共享额度台账（R-4）。D-21 本身需甲方追认（C-8） |
| 3 | `REFUNDED` 要求运费责任已定，是否会让长期挂起的组永远停在 `REFUNDING`；0001 的 168h 是否足够 | **不会永久挂起，168h 足够。** §5.3 `:329` 的条件是"运费责任已定**且**（无可退运费或已退完）"，`:330` 在责任未定/挂起（0001 168h 内）时保持 `REFUNDING`；0001 §6.5.2 `:260-261` 规定 168h 未判定默认按 `MERCHANT_WAREHOUSE` 补退，因此最长 168h 后责任必被确定、运费被补退或确认不退，组即可进入 `REFUNDED`。没有"无限 `REFUNDING`"的死胡同；168h 定时任务的可靠执行属 0001/ADR 的实现范围。`"或已退完"` 是"责任已定"之后的第二个合取项，不与 `:330` 的挂起规则矛盾 |
| 4 | 是否还有代码级 BLOCKER | **没有。** N-66 的冲突已由"每组全额 + Σ 必须相等 + 不等阻断"消除；N-67/N-68/N-69/N-70 关闭；本轮未发现新的规范性矛盾（详见 §4 的 4 项 ADR 交接注意项，均不构成批准条件）。结论为 `PASS WITH CONDITIONS`，剩余条件只有 C-1/C-8/C-9 |

## 4. ADR-0007 交接注意项（不构成批准条件）

| # | 事项 | 建议由 ADR/ops 落实 |
|---|---|---|
| R-1 | Σ 组上限 ≠ 订单剩余 `captured` 时的"人工裁决"没有 owner/动作定义 | ADR-0007 的恢复协议里指名 owner，并给出"核对是否已由取消/其他流程退完 → 幂等关闭补偿"或"补退差异"的裁决动作 |
| R-2 | 取消（AC-43）的订单级全额退款不进入组额度，可能使此后的 TCC 补偿触发 Σ 阻断 | ADR 选择：取消退款也按组记账，或在"订单剩余 `captured`=0 且已全额退款"时把 TCC 补偿直接判为幂等成功 |
| R-3 | 历史无组单的 G1 额度按"整单剩余"计（AC-51 `:214`），AC-50 的组额度公式对无组行单没有商品/运费拆分 | ADR 明确 G1 的额度口径取整单剩余，并覆盖许可初始化为 `NONE` 后的准入分支 |
| R-4 | TCC 在普通售后运费责任挂起期间先退运费时，后续判责不得二次退款 | ADR 确认组额度台账（0001 S14）为共享唯一账，`REFUNDED` 的"已退完"包含 TCC 的运费退款 |
