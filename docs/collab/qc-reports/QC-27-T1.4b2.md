## 1. 新 release 事件（R-A/INV-44）

| 点 | 设计落点 | 判定 |
|---|---|---|
| subject/字段 | §2.1：`shop.inventory.refund_release_requested.v1`，含 `schema_version/release_id/refund_id/order_no/group_no/source/reason/items[{sku_id,quantity,warehouse_id}]/requested_at` | **正确**；`group_no` 必填、`items[].warehouse_id` 必填（禁止默认 W1），`source` 封闭枚举 |

| PRE-only | §2.2：仅 `PRE_SHIP_REVOKED` 写 release；`POST_SHIP_ALLOWED` 不写（已离仓，走 AfterSales restock） | **正确**；符合 INV-44/AC-50 的“未离仓释放、已离仓回库” |
| 生产者 | Order 在 `AdmitRefund`/`admitZeroRefund` 的准入事务内 append outbox；失败回滚；不直接调 Inventory | **正确**；与 T1.4a R-A 的“持久 release 请求”一致 |

## 6. 非阻断提示

1. `release_id = "rr:" + refund_id` 依赖 `refund_id` 的全局唯一（TCC `tcc:<payment_no>:<group_no>`、售后 `after_sale_no`、缺货 `shortage_refund_id`）；建议在 event 校验中显式要求 `refund_id` 非空且与 `order_no/group_no` 一致，避免拼接出跨组冲突。
2. 多仓场景下 `items[].warehouse_id` 必填，但同一组跨仓是否允许一个 group 多仓释放需与多仓协议对齐；建议 event 校验“同一 `refund_id` 的 items 的 warehouse 集合稳定”，重放不改变集合。
3. `POST_SHIP_ALLOWED` 不写 release，但若组先 PRE 后 Ship 竞态（release 事件已发出、Ship 已授权），仍需 Inventory 释放幂等 + Fulfillment 运单取消的既有竞态测试；建议在 T1.4b2a 的测试中补“PRE 事件在途 + Ship 胜出”的组合。
