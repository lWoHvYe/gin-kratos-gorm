## 1. 问题

T1.4b1 仅靠 Payment per-call captured cap：外部部分退款 1000 时，G1 6000 可成功、G2 4000 被拒，造成部分打款。preflight/每笔前重读只能缩小窗口，无法消除 preflight 后外部退款竞态。AC-65 要求“不得部分打款”。

## 2. 契约增量（C-04）

新增 Payment RPC：

```proto
rpc RefundBatch (RefundBatchRequest) returns (RefundBatchReply);
message RefundBatchItem { string refund_id = 1; int64 amount_cent = 2; }
message RefundBatchRequest {
  string payment_no = 1; string batch_id = 2;
  repeated RefundBatchItem items = 3; string reason = 4;
}
message RefundBatchReply { string batch_id = 1; string status = 2; int64 refunded_cent = 3; }
```

语义：
- 在 Payment intent 行锁内校验 `Σ items == B` 且 `Σ items <= captured - refunded`；任何不满足 → `INSUFFICIENT_REMAINING`/`BATCH_SUM_MISMATCH`，**零写入**。
- 全部 item 在同一事务写 refunds/outbox；全成功或全失败。
- 幂等键 `batch_id`；重复请求返回同结果，不重复退款。
- `payment.refunded` 每 item 发 `refund_id`；Order 收敛 commitment/app/batch。

## 3. Order 预检（T1.4b1-R）

任何 `RefundBatch` 前：
1. `B = batch.sum_group_cap_cent` 冻结值；
2. `GetIntent` 取 `R = captured - refunded`；
3. 对每 application `GetRefundByKey(payment_no, refund_id)`：
   - SUCCEEDED/REFUNDED → done；
   - PENDING/PROCESSING → inFlight；
   - commitment SETTLED → done；
   - application DONE 但无 Payment 事实 → unknown；
   - RESERVED → outstanding。
4. 校验 `B == done + inFlight + outstanding`；`R == B - done`；`unknown==0`；否则 `MANUAL_HOLD`、零 Payment。
5. `inFlight>0` 只收敛同 refund_id；`inFlight==0` 才调用 `RefundBatch` 一次。
6. `RefundBatch` 失败：瞬时保持 PAYING 重试；判定性 MANUAL_HOLD；不逐组退化为 Refund。

## 5. 测试矩阵

- 外部退款 1000/6000/4000：零 Payment.RefundBatch、MANUAL_HOLD、无组 SETTLED。
- 本批 G1 已退未投影：done=6000，R=4000 只退 G2。
- 事件丢失：GetRefundByKey 成功不重付；batch 不提前 DONE。
- in-flight：不开始新组。
- RefundBatch 原子性：preflight 后外部退款，batch 全失败/零写入。
- 幂等：同 batch_id 重复、并发。
- 不部分打款：任一组失败，其他组不得已退。
