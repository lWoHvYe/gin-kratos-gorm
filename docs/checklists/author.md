# Author checklist（非规范）

> 操作辅助，冲突以宪法/AGENTS 为准。目标：在提交审查前自己先挡住“趋易避难/自我妥协”。

## 1. 开始前

- [ ] 已读宪法、AGENTS、当前 Spec/ADR；不是只看摘要。
- [ ] 已判定变更类型：契约/feature、实现变更、bugfix；无法归类按契约变更。
- [ ] 契约变更：已列出上游 Spec/ADR/INV 的批准状态；未批准/未决业务题先停。
- [ ] 现状可复现：测试/命令/`文件:行号`；不是凭印象。

## 2. 写 Spec/plan

- [ ] Spec 只写业务、AC、状态所有权、异常恢复；机制在 ADR/plan，不塞进 Spec。
- [ ] 每条 AC 可判定，能落到测试/契约检查/可观测指标；无 AC 的条款不算验收。
- [ ] 状态机无死胡同；并发/超时/部分成功/崩溃/重复/乱序有预期行为。
- [ ] 5 个窗口逐条回答：本地提交后崩溃、RPC 成功后崩溃、重复/乱序、取消/确认竞态、
      外部重放缺失；每条有恢复所有者。
- [ ] 没有用 if-else/局部锁/默认放行掩盖协议问题；同一路径 2 处以上状态分支就停。
- [ ] 延期/豁免有 owner、expiry、范围；没有“以后再说”。

## 3. 写代码前

- [ ] 已确认没有更简的等价方案；没有为了赶进度砍分支。
- [ ] 没有 TODO/空实现/静默 catch 掩盖核心逻辑；异常要么阻断，要么持久补偿。
- [ ] 依赖缺失/配置缺失 fail-fast；没有 nil 默认放行。
- [ ] 事务/幂等/Outbox 有唯一约束或 CAS；不是只靠 Redis。
- [ ] 先做状态机/并发，再做 CRUD。

## 4. 交付前

- [ ] 实际执行日志绑定 `git rev-parse HEAD`；不是“跑过了”。
- [ ] 【测试范围】【未覆盖范围】【取舍】写清楚。
- [ ] 异常分支至少一个；mock 符合真实边界。
- [ ] 受影响的其他 Spec AC 已列出并有非回归证据。
- [ ] 作者没有自标 AC `[x]`；AC 状态留给审查者。
- [ ] commit trailer 不冒充 review；未审写 `Reviewed-by: pending`。

## 5. 自问

1. 并发/超时/部分成功时，系统会怎样？谁恢复？
2. 有没有绕过架构加 if/flag/锁？
3. 向现实妥协了什么？这个妥协是否应该先回 Spec/ADR？
