## 1. 问题

T1.4b1 仅靠 Payment per-call captured cap：外部部分退款 1000 时，G1 6000 可成功、G2 4000 被拒，造成部分打款。preflight/每笔前重读只能缩小窗口，无法消除 preflight 后外部退款竞态。AC-65 要求“不得部分打款”。

## 2. 契约增量（C-04）

新增 Payment RPC：

```proto
rpc RefundBatch (RefundBatchRequest) returns (RefundBatchReply);
message RefundBatchItem { string refund_id = 1; int64 amount_cent = 2; }
message RefundBatchRequest {
  string payment_no = 1; string batch_id = 2;
  int64 expected_total_cent = 3;
  repeated RefundBatchItem items = 4; string reason = 5;
}
message RefundBatchItemResult { string refund_id = 1; string refund_no = 2; string status = 3; int64 amount_cent = 4; }
message RefundBatchReply {
  string batch_id = 1; string status = 2; int64 refunded_cent = 3;
  repeated RefundBatchItemResult item_results = 4;
}
```

语义：
Reply 语义（C-04 §2.6/§2.7）：
- `status=REFUNDED`：本批全部 item 本次退款成功；`status=ALREADY_REFUNDED`：全部 item 已存在同 refund_id/amount 的退款（幂等命中），不重复发事件。
- `refunded_cent = Σ items`（本批金额），不是 intent 总 refunded；不得返回错误的总退款额。
- `item_results[]` 每项：`refund_id`、`refund_no`、`status=REFUNDED|ALREADY_REFUNDED`、`amount_cent`；顺序不保证，Order 按 refund_id 收敛。
- 错误码（零写入）：`INVALID_BATCH`、`BATCH_SUM_MISMATCH`（Σ != expected_total）、`INSUFFICIENT_REMAINING`、`IDEMPOTENCY_CONFLICT`（同 batch_id 不同 items）、`ITEM_CONFLICT`（同 refund_id 不同 amount）、`BATCH_UNAVAILABLE`。
- 在 Payment intent 行锁内校验 `Σ items == expected_total_cent`（Order 的 outstanding）且 `Σ items <= captured - refunded`；`B` 只在 Order 预检；任何不满足 → `INSUFFICIENT_REMAINING`/`BATCH_SUM_MISMATCH`，**零写入**。
- 全部 item 在同一事务写 refunds/outbox；全成功或全失败。
- 幂等键 `batch_id`；同 batch_id 不同 items → `IDEMPOTENCY_CONFLICT`/`ITEM_CONFLICT` 零写入；既有同 refund_id/amount 返回 `ALREADY_REFUNDED`。
- C-05 新增 `refunds.batch_id` + `UNIQUE(payment_no,batch_id,refund_id)`（或 `payment_refund_batches` 表）；per-item 结果持久化。**必须处理 `payment/0001` 的 `uk_refunds_idem(payment_no,amount_cent,reason)`**：同 payment 同金额/同 reason 的多个组会被旧键拒绝；C-05 放宽/删除旧键，统一以 `(payment_no,idempotency_key)`（`refund_id` 即 idempotency_key）为幂等键，并保留 batch 唯一键。
- `payment.refunded` 每 item 发 `refund_id`；Order 收敛 commitment/app/batch。

## 3. Order 预检（T1.4b1-R）

任何 `RefundBatch` 前：
1. `B = batch.sum_group_cap_cent` 冻结值；`done` 只计 SETTLED/GetRefundByKey 成功；`inFlight` 计 PENDING/PROCESSING；`outstanding = B - done - inFlight`；
2. `GetIntent` 取 `R = captured - refunded`；
3. 对每 application `GetRefundByKey(payment_no, refund_id)`：
   - SUCCEEDED/REFUNDED → done；
   - PENDING/PROCESSING → inFlight；
   - commitment SETTLED → done；
   - application DONE 但无 Payment 事实 → unknown；
   - RESERVED → outstanding。
4. 校验 `B == done + inFlight + outstanding`；`R == B - done`；`unknown==0`；否则 `MANUAL_HOLD`、零 Payment。
5. `inFlight>0` 只收敛同 refund_id，超时/未知 → MANUAL_HOLD；`inFlight==0` 才调用 `RefundBatch`，`expected_total_cent=outstanding`。
6. `GetRefundByKey` 成功但 `payment.refunded` 丢失 → Order lazy reconcile（持久 task/worker），batch 不得永久 PAYING；事件重放幂等。
7. `RefundBatch` 失败：瞬时保持 PAYING 重试；判定性 MANUAL_HOLD；不逐组退化为 Refund。

## 5. 测试矩阵

- 外部退款 1000/6000/4000：零 Payment.RefundBatch、MANUAL_HOLD、无组 SETTLED。
- 本批 G1 已退未投影：done=6000，R=4000 只退 G2。
- 事件丢失：GetRefundByKey 成功不重付；batch 不提前 DONE。
- in-flight：不开始新组。
- RefundBatch 原子性：preflight 后外部退款，batch 全失败/零写入。
- 幂等：同 batch_id 重复、并发；同 batch_id 不同 items → `IDEMPOTENCY_CONFLICT`；同 payment 同 amount/reason 两个组原子成功；既有 item + 新 item 混合；GetRefundByKey 超时；事件丢失重放/lazy reconcile。
- 不部分打款：任一组失败，其他组不得已退。
