## 1. 结论

**PASS WITH CONDITIONS。** 本版的 5 个 QC-02 BLOCKER 已在 Spec 层面全部处理：Q-03 不再声称"已获授权"，而是如实申报 `docs/specs/0001` 第 287 行冲突并要求 0001 升版 v1.3（`:423-425`、D-17 `:410`）；N-01 增加 `RESTOCKED`（`:77`、`:227`、`:309`）；N-02 用 AC-47 归因 + D-11 上限替代"超时未决"（`:171-174`、`:404`）；N-03 明确 `CONSUMED ≠ SHIPPED`（`:85`、`:290-291`、`:189`）；N-04 由 INV-44 + AC-50 末条补齐释放执行方与失败语义（`:112`、`:196`、D-18 `:411`）。

仍有 4 项 MAJOR（N-23…N-26）是资金/库存/缺货路径上的可判定性缺口，另有 10 项 MINOR 与 5 项部分关闭。它们都能在不推翻架构的前提下用条款补齐，因此不判 `BLOCKED`；但在 §7 条件关闭前不得批准。

**判定为条件的边界**：Q-03 依赖的 0001 v1.3 是**外部契约批准**，不是 0002 可自行关闭的缺陷；只要 0002 满足"如实申报 + 未批准前不得 approved"，它就从 BLOCKER 降为批准顺序条件（C-1）。本报告不接受"先在 0002 里解释、批准后再补 0001"的做法。

## 5. 六项重点攻击的逐条回答

| # | 攻击点 | 回答 |
|---|---|---|
| A1 | `PAID` 前置"所有行 `CONFIRMED`"与"`PAID` 不表示库存已确认"是否还有语义冲突 | **没有遗留的硬冲突，但措辞仍需收口。** v1.1 已删除"不表示库存已确认"（v1.0 的问题句），`:37` 改为"已接受支付且结算前预留已确认，但不表示可发货"。`PAID` 仍是既有 `orders.status` 值、由单点 CAS 写入，"所有行 `CONFIRMED`"是迁移守卫而非新字段，与基线 INV-06"确认在标记支付之前"（`docs/architecture-baseline.md:204`）及 0001 E7（`docs/specs/0001-...md:412`）同向；AC-48 `:177` 在 `PAID` 之外重复校验 `CONFIRMED` 是必要的，因为 `PAID` 只声明进入时刻、组退款后行可被释放（S4 `:74`、INV-44 `:112`）。残余是 `:37`"不承担库存…语义"的措辞（N-32）。与 INV-38/AC-27 的边界也自洽：两者约束支付后组退款，本版把"全有或全无"限定在 `PENDING_PAYMENT→PAID`，支付后的组退款交给 D-17/0001 v1.3（C-1） |
| A2 | D-17 的 0001 升版请求是否足以解决 Q-03，还是仍属"未批准就依赖" | **作为 Spec 缺陷已解决，应降为条件 C-1。** 判据：(a) 不再声称已获授权，而是引用 0001:287 的明文禁令（`:424`）；(b) 明确"本 Spec 不单方面改写"并声明"未批准前不得 approved"（`:425`）；(c) 给出备选（整单退款）及其与 AC-27/INV-38 的冲突（`:424`）。这满足"如实申报 + 阻断面向上游"的最低要求。但 0002 仍是"未批准就依赖"：C-1 必须规定 0001 v1.3 **先于** SPEC-0002 批准，且升版必须写明被修改条款（0001:287、§6.6、§7.5）、影响的 INV-06/INV-26/AC-27，以及组退款释放/回库边界；若甲方选"任何组退款都整单退款"，则必须同步修订 INV-38/AC-27。在此之前 INV-44/AC-50 末条只能作为草案条款存在 |
| A3 | `CONSUMED + CREATED` 的取消路径是否真的消除"退款后仍可发货"，Ship/取消 CAS 是否可判定 | **路径成立，但判据不完整。** `:88`、`:189`、`:291` 规定退款准入取消 `CREATED` 运单、Ship 与取消在运单行 CAS、Ship 先胜则退款转 `POST_SHIP_ALLOWED`——这三个要素足以消除"退款后仍发货"：取消胜出后运单为 `CANCELLED`，Ship 的 CAS 期望值（`CREATED`）不再成立；Ship 胜出则退款按已离仓处理。问题在于"未离仓"没有定义（`:190` 只反问列举 `SHIPPED/EXCEPTION`），导致**同一 `refund_id` 在"已取消运单、未记录结果"处的崩溃重试**和**同一组第二次部分退款**无法从条款直接判定，只能推断（N-23）；此外 Ship 败者没有返回码（N-34）。补齐这两点后窗口 2 才算真正闭合 |
| A4 | `RESTOCKED` 是否与 0001 §6.6/AC-30 的 48h 默认退款冲突（例如补货在 48h 后到达） | **与 48h 默认退款不冲突。** 0001 §6.6/AC-30 的 48h 默认只在"用户未选择"时生效（`docs/specs/0001-...md:285`、`:576-578`；本版 AC-56 `:225` 同样写"用户未选择"），用户选择等待后由补货日期接管（AC-56 `:226`、D-15 `:408`），因此补货在 48h 后到达不是"默认退款"能覆盖的场景。真正的缺口有两个：①`NOTIFIED` 状态下补货先到（用户尚未选择）没有迁移（§5.4 `:309-311` 只有 `RESOLVED_WAIT→RESTOCKED`），而 AC-56 `:227` 允任意时刻置 `RESTOCKED`（N-24）；②案件已 `RESOLVED_REFUND`（含 48h 默认退款）后补货到货无处置，若实现为 `RESTOCKED` 会恢复已退款组的发货（N-29）。另：案件期间预留是否保持 `CONFIRMED` 未声明，直接影响 `RESTOCKED` 后能否满足 AC-48（N-24） |
| A5 | 同组多部分退款与 `REFUNDED` 判定、Payment 额度基准是否自洽 | **额度基准方向正确，但有两个缺口。** 自洽面：S9 `:79`/§5.3 `:302` 允许多个 `refund_id`；AC-55 `:218` 与 §5.3 `:304` 规定退款完成以 Payment 为准；AC-53 `:209-211` 的订单级 captured/refunded 只计生效支付，与 `architecture-baseline.md:200`（INV-02）和 0001 INV-24（`docs/specs/0001-...md:150`）兼容——只要 ADR 把 Payment 的订单级 captured 实现为同一口径。缺口：①"该组剩余可退额度"的层级未声明（行/组/订单），0001 INV-24 是行 + 订单双层（N-31）；②`REFUNDED` 只写了"额度=0"这一必要条件，未写"所有 `refund_id` DONE ∧ Payment 已退覆盖"的充分条件（N-31）；③更实质的是 N-26：未离仓组的部分退款会取消整票运单，余量无法继续履约，规格必须裁决"整组退款还是余量重建运单" |
| A6 | 是否还有死胡同/非法迁移/无错误码/不可判定的"或" | 有，均已列入 N-23…N-34：**死胡同**——N-24（若案件期间释放预留，`RESTOCKED` 后永久禁发）、N-26（未离仓部分退款后余量永不发）；**非法/缺失迁移**——NOTIFIED→RESTOCKED 缺（N-24）、`PAID→CANCELLED` 未显式列为非法（建议补在 §5.1）、迟到补货到货未定义（N-29）；**无码/双码**——AC-48 `:179`、§5.1 `:276`、AC-56 `:229`、AC-59 `:248`、Ship 败者、AC-47 超时分支（N-28/N-34）；**不可判定的"或"**——AC-48 `:179`、§5.1 `:276`、AC-56 `:229`、§8 `:379`、E2 `:351`"就绪"（N-28/N-34） |
