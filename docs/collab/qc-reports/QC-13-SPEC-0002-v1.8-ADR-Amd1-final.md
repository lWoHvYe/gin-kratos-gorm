## 2. BLOCKER（1 条）

### B-1 SPEC r5 与 ADR r3 对“Payment.Refund 与 `EXPIRED_REFUND` 终态的先后”表述相反

- SPEC：`docs/po/drafts/0002-v1.8-amendment.md:154`“上述补偿完成后，**Payment.Refund 最后执行；全部成功后才置 `EXPIRED_REFUND`**”；`:155`“IF 补偿失败/超时…保持 `COMPENSATING`”；`:164` D-22 同。
- ADR：`docs/adr/0007-payment-settlement-admission-amd1.md:297`“CAS `COMPENSATING→EXPIRED_REFUND` + 写 `refund_applications`；支付级退款由 Order worker 在**终态后**执行，Payment.Refund 是最后一步”；`:341` 同。
- 风险：实现者按 SPEC 会把 Payment.Refund 放在 `EXPIRED_REFUND` 之前；按 ADR 会放在之后。两者对“打款失败时队列停在 `COMPENSATING` 还是 `EXPIRED_REFUND`”“`EXPIRED_REFUND` 是否代表已退款”给出不同答案，属于同一业务状态的两种语义，不能同时批准。
- 建议：二选一并同步两份文本。若以 ADR 为准（终态后打款）：SPEC 改为“补偿完成 → 置 `EXPIRED_REFUND` + 写支付级申请 → worker 打款；打款失败保持 `EXPIRED_REFUND` 的申请 `FAILED_PERMANENT`/重试，不回 `COMPENSATING`”；若以 SPEC 为准（打款后终态）：ADR 改为“Payment.Refund 成功后 CAS `COMPENSATING→EXPIRED_REFUND`；失败保持 `COMPENSATING`”。无论哪种，`refund_applications` 的写入与终态的原子性需同事务。
