# 业务需求池（未立项）

> 来源：2026-11-22 项目体检 + 后续裁决。这里只放**尚未有 Spec 覆盖**的业务能力；已覆盖的以 SPEC 为准。
> 排序原则：资损与合规 > 用户承诺与体验 > 能力扩展 > 范围待定。

## Tier 0 — 资损与合规（不做完不许对外承诺 SLA）

| ID | 业务缺口 | 为什么现在做 | 现状证据 | 依赖 |
|---|---|---|---|---|
| R-01 | **退款审批授权矩阵**：≤X 元谁批、>X 元谁批、越权拦截、超时效/超额度例外放行链 | 目前只有单一"审核"动作，没有按金额分级的授权；SPEC-0001 只定金额计算，不定谁有权批 | 售后仅 `Approve` 动作，无审批分级 | 无，可独立立项 |
| R-02 | **日终四方对账与差异处置**：支付流水 / 订单应收 / 售后退款 / 库存变动的对平口径、差异分类、处理时限、客户话术 | ADR-0005 §11 只定义对账等式，业务 SOP 与差异处置完全没有 | `docs/adr/0005` §11 仅"等式" | 依赖 R-01 的差异处置权限 |
| R-03 | **营销资源返还**：整单/部分退款后优惠券、满减额度、积分是否返还及口径 | SPEC-0001 只规定"按退款比例释放额度"，未定义是否把券退回用户 | SPEC-0001 R 章节只到额度释放 | 无 |

## 立项门槛（避免又变成"什么都没做完"）

一份需求进入 Spec 前必须能回答：

1. 影响的是钱、货、还是体验？**钱与货优先**。
2. 现有状态字段能否承载，还是需要新的事实所有者（State Ownership 必须写清）。
3. 异常分支至少覆盖：并发、超时、重复投递、部分成功、进程崩溃后恢复。
4. 谁是验收人，验收数据从哪来。
